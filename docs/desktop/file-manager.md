# File manager — Nautilus + gvfs

**Selection:** Nautilus (GNOME Files, standalone) with gvfs virtual backends, its own thumbnailers, and shared freedesktop trash with a declarative 30-day purge. Complement to yazi, not a replacement (#762, revised #771).

## Premise

Yazi remains the terminal browse surface and keeps the removable-media safe-eject role ([removable-media.md](./removable-media.md)). This selection adds the capabilities a TUI structurally cannot provide: drag-and-drop into browser upload dialogs and GUI apps, thumbnail-grid visual browsing, and the virtual backends — phone (MTP), network shares (SMB/NFS), `trash://`. This is the revisit clause in removable-media.md §Alternatives firing: "gvfs earns its place only if phone/MTP or network shares become a need; revisit then." Both needs are now real.

Premise verified before designing (selecting-tooling step 0): the running closure carried zero gvfs, no GUI file manager, no thumbnailer — the gap is real, not a config oversight.

## Rationale

**The virtual-backend need is settled by gvfs, not by the file-manager pick.** Every maintained GTK-family candidate sits on the same gvfs/GIO daemon set; only Dolphin (KIO) differs. The nixpkgs gvfs default build already includes the MTP, SMB, NFS, and archive backends, and `services.gvfs.enable` wires D-Bus services, FUSE, and libmtp udev rules in one switch. The frontend tiebreakers are therefore outside-DE cleanliness, toolkit, theming, and NixOS wiring.

**Runtime theme/polarity compatibility is now the decisive criterion — and it inverts the earlier toolkit call.** #766 picked Thunar on GTK3's full widget-theme fidelity: it rides the existing 34-key `@define-color` render (ADR-044) with real widget coverage, where libadwaita surfaces consume only the named colours (the mechanism in [audio.md](./audio.md)). That fidelity turned out not to travel: empirical probes on alcyone (2026-08-11) found a native-Wayland GTK3 process gets **no runtime theming signal at all** on this stack — a `theme light` swap did not repaint a running Thunar window, and Thunar's persistent background daemon means even closing and reopening the window doesn't pick up the flip, only a full daemon restart does. A GTK4/libadwaita probe (gnome-text-editor) flipped the other way: on `theme light` the **running** window went dark→light live via the portal's `color-scheme` signal — the structural polarity-follow was real, later confirmed directly on Nautilus. The named-colour half of that original read was wrong: #777 found the conductor's gtk4 render inert on this pin under both syntaxes it emitted (`@define-color`, and `:root { --*-color }`, which loses to libadwaita's own variable definitions) — GTK4 apps had been rendering stock Adwaita all along, so the "re-read the swapped CSS" observation was two visually-identical stock-grey windows, not a palette follow. #777 fixed the render by scoping the same variables on `window { }` instead, which does paint; the fixed-render probe matrix (Nautilus, 2026-08-11) confirmed a fresh launch shows the palette, and a live polarity flip on a running window repaints both structure and colour with no restart, but a live family flip on a running window does not repaint — it stays on whatever family it launched with until the `prefers-color-scheme` portal signal fires again (a fresh process launch always picks up the current family; see §Sharp edges for the live-family-flip gap). So the honest trade is: GTK3 buys full widget-theme fidelity that latches at launch; GTK4/libadwaita buys narrower (named-colour-only) fidelity that follows the theme-menu conductor's live polarity flips but not, without an explicit signal bounce, live family flips. With the desktop used continuously across polarity switches, live-follow still outweighs full-widget fidelity.

- **Measured marginal closure is modest, and it's mostly gvfs already sunk.** Nautilus's own closure against the current running system (which already carries Thunar + gvfs + tumbler from #766): 50.9 MiB across 21 new paths — GNOME-specific libs (libglycin, libportal-gtk4, gnome-autoar, gnome-user-share) plus tinysparql/localsearch (§Sharp edges). gvfs itself contributes nothing marginal since it's already installed and stays either way.
- **Maintenance is healthy.** GNOME-core team maintenance, pin carries 50.2.2, GTK4/libadwaita native Wayland; the community-conventional pick among full desktop environments, now also compatible with this stack's runtime-theming design.

Accepted costs: no first-class NixOS module — verified against the pin, there is no `programs.nautilus` option, so it installs as a plain `environment.systemPackages` entry, the same shape as any other GUI app without one (ADR-006's ENHANCE criterion no longer applies in Nautilus's favour); and the tinysparql/localsearch build coupling, carried as a sharp edge rather than enabled day one (see below). The `xdg-portal.nix` FileChooser routing to the gtk backend is unaffected either way — it governs which portal *implementation* answers `FileChooser` (deliberately not `xdg-desktop-portal-gnome`), independent of which file-manager package happens to be installed — so nothing there needs to change for this swap.

## Alternatives considered

- **Thunar** — the previous selection (#766). Native-Wayland since the libxfce4windowing work, a first-class NixOS module (`programs.thunar` + `xfconf`), and full GTK3 widget-theme fidelity — all genuine, none decisive once the runtime-flip criterion applied (§Rationale): a native-Wayland GTK3 window gets no theming signal while running, and Thunar's persistent daemon means even a close/reopen misses a flip.
- **COSMIC Files** — recorded runner-up. 1.5.0 launches, renders, browses, and gvfs volume-monitors standalone under niri (probed live: a USB stick showed in the sidebar with eject). Theme hot-reload is broken standalone, though: it ships with the `dbus-config` Cargo feature, prefers `cosmic-settings-daemon` (only started by `cosmic-session`, not D-Bus-activatable) and retries forever with no fallback to the working inotify path — matching the open upstream [pop-os/cosmic-files#1633](https://github.com/pop-os/cosmic-files/issues/1633) exactly; a restart does pick up new theme files. Marginal closure was modest (249 MiB / 6 paths, zero Qt) but forces `cosmic-settings` (73 MiB) and `pop-icon-theme` (66 MiB) as runtime deps, and both escape hatches fail repo stances: `--no-default-features` means source-rebuilding forever, and running `cosmic-settings-daemon` standalone means adopting a foreign DE daemon for one app. Unprobed additional risk: an open right-click crash under sway ([pop-os/cosmic-files#1414](https://github.com/pop-os/cosmic-files/issues/1414), xdg_popup protocol). **Revisit trigger: upstream #1633 fixed in a shipped nixpkgs build → re-probe.**
- **Dolphin (KDE)** — KIO is a parallel backend universe to gvfs, largest marginal closure, re-imports the twice-evicted Qt stack, and has an open nixpkgs issue (#409986) where "Open with" is broken under non-Plasma WMs, niri named specifically. The "objectively best" folk wisdom does not survive this host's constraints.
- **PCManFM (GTK)** — effectively unmaintained (libfm's last real release 2021, lone caretaker release since). Fails the maintenance bar outright.
- **PCManFM-Qt (LXQt)** — the credible near-miss: actively maintained, cleanest outside-DE story (no settings daemon, no indexer), gvfs-backed. Passed over solely on toolkit: it would re-import a full Qt6 stack (removed twice from this desktop, most recently #644), resurrect `stylix.targets.qt`, and add a theme-menu render target — for a frontend no more capable than Thunar.
- **Nemo (Cinnamon)** — alive under Mint, but the project's testing culture is X11-first (Cinnamon Wayland support is years out); weakest Wayland provenance among the maintained GTK options.
- **Caja (MATE)** — no capability the others lack, slower cadence, older lineage. No reason to pick it.

## Trash

**Policy: trash-by-default on both surfaces, bounded by a declarative purge.** Yazi's stock keymap already follows the freedesktop Trash spec (`d` trashes, `D` deletes permanently) and Nautilus's delete does the same, so both surfaces share one spec'd location (`~/.local/share/Trash`, per-volume `.Trash-1000/` on other filesystems) with interoperable restore metadata. With ADR-034's no-host-data-backup stance, trash is the only undo layer the fleet has — and a GUI makes accidental deletion (mis-drag, fumbled selection) more likely than a typed command ever did, so adding the GUI without the safety net would be the worst combination.

The bound: a systemd user timer runs `trash-empty -f 30` (trash-cli) daily — deleted files are recoverable for 30 days, then genuinely gone. No native module exists for this in NixOS or home-manager (verified in the locked sources); the hand-authored-unit-in-Nix pattern is the accepted shape here (polkit agent, noctalia units, ephemeral-root purge). GNOME's `remove-old-trash-files` gsetting was rejected as inert on this stack — it is enforced by gsd-housekeeping, which only runs inside a GNOME session (set ≠ enforced).

Ephemeral root does not interact: the boot rollback archives only the `@root` subvolume; `/home` — where the trash, Nautilus's dconf state, and thumbnail cache all live — is untouched, so no persist-whitelist entry is needed.

## Configuration

- **System** (`modules/nixos/file-manager.nix`, in the system desktop-env bundle): `environment.systemPackages = [ pkgs.nautilus ]` — no NixOS module exists for it (verified against the pin). `services.gvfs.enable` unchanged (default full-backend build from the binary cache — the deliberate whitelist act is enabling gvfs at all; trimming build flags would force source rebuilds of gvfs on every nixpkgs bump for marginal gain). `services.tumbler` is dropped: Nautilus wraps its own thumbnail loaders (gdk-pixbuf/libjxl/librsvg/webp) into `XDG_DATA_DIRS` at build time (verified in the derivation's `preFixup`), so the Xfce D-Bus thumbnailer it used to delegate to is unused.
- **localsearch/tinysparql**: `services.gnome.localsearch` and `services.gnome.tinysparql` exist as NixOS options in this pin (verified), and Nautilus links `tinysparql` + `localsearch` as `buildInputs` (verified in the derivation) — but that's a link-time dependency for full-text search integration, not a hard runtime requirement; nothing in the derivation or nixpkgs indicates a hard-fail without the miner running. Left disabled day one, deliberately — see §Sharp edges for the enable trigger.
- **Home** (`home/nixos/file-manager.nix`, in the home desktop-env bundle): the daily trash purge timer (§Trash) + `trash-cli`; `xdg.mimeApps` registers `org.gnome.Nautilus.desktop` (verified — the `.desktop` file name inside the built package) for `inode/directory` only — the register-only-exercised-types discipline ([firefox.md](./firefox.md) precedent).
- **Keybind**: `Hyper+F` → Nautilus, same chord as before (only the spawned binary changed), as one cross-platform capability with macOS's focus-or-launch Finder (the former `open-finder` entry folded in) — exact chord parity, in the bind registry per [keybinds.md](./keybinds.md) cadence (own commit). The chord was freed by an operator taxonomy call in the original work: the window-geometry cluster (`F`/`M`/`C`/`R`/`−`/`=`) migrated from bare `Hyper` to `Hyper+Shift`, sharpening the principle to "bare Hyper navigates and launches; Shift acts on the window" — see keybinds.md §The organizing principle.
- **Icons + cursor**: a GUI file manager is the first surface where the unwired icon theme (#110) becomes visible, so that gap lands on this work's critical path — as its own selection, [pointer-icons.md](./pointer-icons.md).
- **SMB credentials**: deferred until an authenticated share exists; gnome-keyring + libsecret are already present, so the path is there when needed.

## Sharp edges

- **Drag-and-drop is gated on niri, not the file manager.** Open niri issues cover native-Wayland DnD (YaLTeR/niri#2446 — FM→browser drops failing; #3162 — missing drag icons), and Wayland→XWayland DnD doesn't work at all (Firefox runs native Wayland, so the critical path avoids it). Runtime probe required before this selection is called done.
- **gvfs mounts need the polkit agent.** mate-polkit's still-pending smoke test (polkit.md §Sharp edges) names exactly this trigger — mounting from a file manager discharges it.
- **home-manager #7143**: `dconf.enable` can clobber `GIO_EXTRA_MODULES` and silently break gvfs. This config enables dconf (GTK theming), so the interaction must be probed at activation.
- **localsearch/tinysparql absent = degraded search, not a crash (verified, §Configuration).** Full-text and metadata search inside Nautilus will be weaker or unavailable without the miner running. Enable trigger: search feels meaningfully degraded or unstable in practice — flip `services.gnome.localsearch.enable` and `services.gnome.tinysparql.enable` together when that's observed, not preemptively.
- **Thumbnails are image-formats-only day one.** Nautilus's wrapped loaders cover images (§Configuration); PDF/video/font/office thumbnails need freedesktop `.thumbnailer` providers (evince, a video thumbnailer, …) that this config doesn't carry — not a consequence of dropping tumbler (Nautilus never consumed it; verified against its source), but an observable step down from the Thunar+tumbler era. Each provider earns its place if missed in practice.
- **samba is the closure bulk.** Most of gvfs's marginal closure is the SMB client stack — the price of the network-shares requirement, not of the file-manager pick.
- **Icons still latch on runtime flip.** `gtk.iconTheme` is baked at build, not wired to the theme-menu conductor's runtime polarity switch — a GUI file manager is the first icon-heavy surface where that's visible daily. Tracked in [pointer-icons.md](./pointer-icons.md) §Sharp edges as the recorded follow-up.
- **Live family flips don't repaint a running GTK4 window; polarity flips do.** #777's fixed-render probe matrix (Nautilus, 2026-08-11) found a running window ignores a family swap (e.g. `theme gruvbox`) until the `prefers-color-scheme` portal signal fires again — a fresh launch always picks up the current family, and manually bouncing the `color-scheme` dconf key (write the opposite value, ~300ms, write it back) forces a running window to re-read too. A same-effect bounce has been added to the `theme` CLI's family branch (staged on `777-gtk4-window-vars`, not yet built into a system generation or verified end-to-end through the real command) — until that lands and is confirmed, treat a live family flip as needing a Nautilus close/reopen.

## Verification (runtime, before done)

Per the set ≠ enforced rule, on a desktop host after activation: **open Nautilus, then run `theme light` (or `dark`) while it's still open — the running window must follow live, no restart** (this is the criterion that decided the selection; originally probed via the gnome-text-editor proxy on 2026-08-11, since confirmed directly on Nautilus — also 2026-08-11, under #777 — after #777's window-scoped-variable render fix; the gtk4 render this criterion was originally scored against turned out to be inert, see §Rationale). The same criterion does **not** hold for a live family switch (`theme <family>`): a running window stays on its launch-time family until the `prefers-color-scheme` portal signal fires again — see §Sharp edges. Also still pending: drag a file from Nautilus into a Firefox upload dialog; trash a file in yazi → restore it in Nautilus's `trash://`; trash on a USB stick → `.Trash-1000/` appears at the stick's root; connect a phone → MTP mount appears; mount an SMB share by `smb://` URI (auth prompt via mate-polkit — discharges the polkit smoke test); confirm the purge timer with `systemctl --user list-timers`.

## History

#766 selected Thunar (2026-08-11) on GTK3's full widget-theme fidelity and its first-class NixOS module. The runtime-flip criterion emerged the same day from operator use — the theme-menu conductor's live polarity flip exposed a gap the original selection hadn't been tested against: a native-Wayland GTK3 window receiving no runtime theming signal at all. Probes run under #771 confirmed the GTK3 latch and appeared to validate GTK4/libadwaita's live named-colour follow, flipping the selection to Nautilus. That named-colour read was later found to be a false positive: #777 established the conductor's gtk4 render was inert under both syntaxes it emitted at the time, so what #771 actually observed was two visually-identical stock-Adwaita windows flipping structurally via the portal's dark/light signal, not a palette follow — #777 fixed the render (variables scoped on `window {}`) to make the named-colour follow real. COSMIC Files was evaluated as runner-up and deferred on the open upstream issue pop-os/cosmic-files#1633 (broken standalone theme hot-reload); revisit when that's fixed in a shipped nixpkgs build.
