# Fleet service placement — criticality, failure domains, and the standing service-tier arbitration

**Status:** Accepted (2026-08-11) — design note (`docs/design/`). Not built (rules and triggers only, by design — R1–R6 produce no placements to build; ADR promotion deferred, per the operator's decisions recorded in [#387 on 2026-08-11](https://github.com/dannyfaris/nix-config/issues/387#issuecomment-5251614181)). #387 — the arbitration its comments asked the design note to carry ("candidate shapes to weigh… none selected"); sibling of [fleet-service-isolation.md](./fleet-service-isolation.md) (the isolation axis); jointly they are the "central homelab ADR" #387 names. Adjacent #547 (closed, name banked), #557, #566, #569, #638, ADR-030, ADR-034, ADR-042. Drafted 2026-07-07 against metis's then re-role premise; reworked 2026-08-11 onto #387's 2026-08-03 retirement re-cut — metis exits the fleet rather than re-roling, and this note's proper nouns follow that decision throughout.

## Summary

*Where* a service runs — which host, in which failure domain — is the second axis of #387's service architecture, orthogonal to how sandboxed it is. The operator's own 2026-07-06 comments arbitrated capacity across three criticality classes (accelerators / watchers-last-resorts / products) and a role map; what they left deliberately open was the products class's shape. This note develops that open question into **conditional decision rules with triggers rather than placements**, honouring the recorded "open input, not a decision" instruction — a construction that survives #387's 2026-08-03 re-cut untouched, because it never named a placement metis's retirement could strand. Three findings drive it, two of them operator-endorsed 2026-08-11. First, the comment record self-corrects when read in order: the 09:26 always-on/bursty split retired the noisy-neighbour scenario the 08:57 products-isolation case was built on, leaving **maintenance-cadence coupling** — the weekly bump's kernel updates versus an uptime-expecting co-tenant — as the settled surviving residual, ADR-030's trigger-3 with a concrete mechanism (Correction 1, endorsed). Second, on inspection **the "products tier" dissolves as a placement category**: Home Assistant is sui generis (hardware coupling + uptime expectation), and the remaining members decompose into per-service facts the isolation rule and the backup seam already answer (the dissolution lean, endorsed; R6 reconstitutes the category if a wave arrives). Third, the fleet **violates the watcher rule today, and a deliberate relocation has already failed to fix it once**: #688 moved the fleet's ntfy receiver off metis onto electra, the genuinely always-on host — but every host's failure alerts, electra's own included, still terminate at electra's own ntfy, so electra-down means fleet-wide silence, including about electra. The violation moved; the rule that would have prevented it (R1) was not consulted at the move. That is this note's headline de-risk finding: the fleet has now chosen "which box is up" over the rule twice, on two different hosts, and only a standing rule — not another one-off relocation — closes the gap.

## Motivation

#387's comments (2026-07-06) did substantial arbitration against the epic's then premise — metis re-roling into the homelab server: three criticality classes (accelerators — degraded-not-broken; watchers/last-resorts — must live in a different failure domain than what they guard; products — uptime-expected, stateful, externally coupled), a role map (always-on metis, bursty tower, #547 Pi sentinel), a hardware direction (~64GB tower), and a parked, trigger-watched inference selection. That arbitration's *classes and rule logic* are not relitigated here — they are this note's input, and they outlived the premise that occasioned them. What was left open, explicitly ("**architecture deliberately unresolved** — the re-role design should treat it as an open input, not a decision"), is the products class's shape: co-tenant on an always-on services host, dedicated host(s), guests on a hypervisor (#555), or a hybrid — with three tensions named for early attention (update cadence, a second automation plane, products state).

Since those comments, #387 itself was re-cut (2026-08-03): metis does not re-role, it **retires from the fleet** — duties relocate first (ntfy already has, #688), then a #634-shaped decommission train, and the ProDesk hardware later returns as a brand-new host, which is explicitly outside this note's scope. The always-on role the comments assigned to "metis" now belongs to **electra** (Lenovo ThinkCentre M920q Tiny, genuinely headless, always-on, live since #637), which already hosts the fleet's failure-alert receiver (relocated by #688) alongside its own unit-failure client. The "bursty tower" the comments anticipated has also arrived and been named: **alcyone** (Gigabyte B550, RTX 4060) is the live flagship desktop, not a hardware plan. The "M720q (name TBD)" the target-fleet table pencilled in has a name and a tracking issue but no hardware yet: **Maia** (#638), still role-TBD, an ADR-042 service-sink slot. The Pi sentinel the comments anticipated remains unbuilt; its name is banked (**Taygeta**, ADR-045, #547 comment 2026-07-25) but the issue that was going to onboard it (#547) closed not-planned on 2026-08-03 when its original aarch64-CI rationale dissolved with nixos-vm's retirement (#634) — there is currently no open issue tracking Pi provisioning, so the sentinel role is a recorded aspiration in #387's comment history, not a scheduled arrival. None of this changes the rules below; it changes which real host each rule reaches for.

The placement question is not hypothetical even today: the fleet already runs infrastructure services (ntfy receiver, unit-failure fan-in, both now on electra), and the first candidate stateful service, keeper (#386, unimplemented), needs retargeting off the retiring host — a decision the operator has recorded as also forcing electra's deferred container-tooling call (#637), not something that can quietly precede it.

The objective, stated solution-free: **a service's host and failure domain should be derivable from declared rules when the service becomes real — decided by its properties and the fleet's topology, not by whichever box is handy on the day.** The failure mode this prevents is live now (De-risk): the alert path was placed by convenience and self-watched as a result, and a deliberate, well-executed relocation preserved rather than fixed that shape, because the move was decided by "which box is always-on" and not by the rule this note formalises.

Forces:

1. **P1 — Failure-domain honesty.** A watcher must not share a failure domain with what it watches; a last-resort must survive the disaster it exists for (#566, #569). This is the class the operator called "only worth having in a different failure domain."
2. **P2 — No host becomes a gate.** Fleet *functions* must not acquire a single-host dependency; pull-based convergence (#552) already guarantees deploys don't, and placement must not reintroduce one elsewhere.
3. **P3 — Uptime-expectation vs maintenance cadence.** The fleet's weekly `nixos-unstable` bump (ADR-030) regularly carries kernel updates; a host applying them needs reboots (uptime blips for every co-tenant) or runs stale kernels (drift the evergreen stance dislikes). A service with real uptime expectations makes that choice visible — ADR-030's own trigger-3.
4. **P4 — Physical coupling is not schedulable.** USB radios (HA's Zigbee/Z-Wave), disks, and displays pin a workload to a box in a way no software placement can move.
5. **P5 — Capacity is not the driver.** The operator's arbitration already established the always-on class is single-digit-GB light; on this fleet, placement decisions are about fate-sharing and cadence, not gigabytes. A rule that reaches for "more capacity" is answering the wrong question.
6. **P6 — Decide when real (accrete).** Placements land when their service does; this note produces rules and triggers, not a service map. The operator's "open input, not a decision" instruction is a constraint on this note, honoured by construction.
7. **P7 — Hardware plans are inputs, not commitments.** This still binds for what has not arrived — Maia (#638) has no arrival date, and Taygeta currently has no tracking issue at all — but alcyone no longer illustrates it: the tower is a live host now, not a plan, so rules that name it name a real failure domain rather than a hedge. Rules must still degrade gracefully wherever the topology has not caught up.

## Design

**The classes and the standing role map (operator's, restated as input).** Accelerators → **electra** (always-on; degraded-not-broken if down — the role the comments called "always-on metis"). Bursty/schedulable → **alcyone** (interactive, may sleep; zero always-on services — the role the comments called "the tower"). Watchers/last-resorts → the Pi/**Taygeta** sentinel, when and if it arrives (different failure domain; must not accrete other roles; currently unbuilt and untracked — see Motivation). Products → open, this note's subject.

**Correction 1 — the comment record, read in order (operator-endorsed 2026-08-11).** The 08:57 case for a dedicated products host was isolation: "a nix build burst must never take down the heating automation." At 09:26 the always-on/bursty split moved every burst to the tower — the noisy neighbour left the building. The operator confirmed this reading on 2026-08-11: the 09:26 split does retire the 08:57 case, and no residual isolation concern beyond bursts was intended to survive it — resolving what the 2026-07-07 draft flagged as its own Drawback 4 (the risk that this correction overreaches the operator's intent). What survives on the always-on host — electra, not the retiring metis the comments assumed — is steady, light co-tenants; the settled surviving residual is **P3's cadence coupling** (smaller residuals — administrative blast radius, disk contention — were flagged as possibly surviving too while this reading was still provisional; the endorsement named none of them, so they are treated as closed unless raised again): the always-on host switches weekly, kernel updates accumulate, and either reboots blip every co-tenant (HA down, Zigbee re-initialising, while the heating decides) or the kernel goes stale. That residual is real but different in kind — it argues about the *services host's maintenance posture*, not about neighbours, and its remedies are posture remedies (ring position, kernel-update discipline, or a stable channel for the services host — ADR-030 trigger-3, which the operator already flagged as fired in this direction) before they are buy-a-box remedies.

**Correction 2 — the products category, inspected member by member (operator-endorsed 2026-08-11).** HA: hardware-coupled (P4), uptime-expected (P3), breaking-cadence upstream — three promoting properties, one of them physical; HA is *sui generis* and will force a real placement decision on its own facts. n8n: stateful, webhook/OAuth-coupled, no hardware, uptime that matters only as its automations become load-bearing — the isolation rule (container, image-pinned) plus the backup seam answer it; its genuinely novel tension is being a *second automation plane* (flagged below), not its placement. keeper (#386, unimplemented — see Motivation): light, tailnet-only, personal-facing — an ordinary always-on-host co-tenant under the isolation rule, once it is retargeted off the retiring host and the container-tooling call (#637) it forces is made. **The operator endorsed this note's dissolution lean 2026-08-11: "products" dissolves as a placement category.** The category, not its members, was generating the buy-a-host question; individually, every current member except HA places trivially under the rules below, and HA deserves a decision at its own arrival with its own facts. If products later arrive as a wave, the category reconstitutes — that is R6's trigger, and it now stands as the hedge on a settled lean rather than a condition on an open one.

**The rules.** Conditional, trigger-carrying, in precedence order — a service takes the first rule whose property it has:

- **R1 — Watchers place across the domain boundary.** Anything that watches, alerts on, or is the last resort for X must not run on X — prefer the Pi/Taygeta sentinel once it exists; any other genuinely independent domain qualifies until then. *Live application, demonstrated twice (De-risk):* the alert path violated this on metis; #688 relocated the receiver to electra without the move being checked against this rule, and the violation moved intact — electra now watches electra. This is the note's strongest evidence for treating R1 as a hard gate rather than a preference: a deliberate, well-executed relocation preserved the exact structural gap it had the chance to close, because placement was decided by "which box is always-on" and not by R1. Until Taygeta (or any other independent domain) exists, the violation is a recorded, accepted gap — not an unknown one — and the first candidate host for the ntfy receiver or a #569-style heartbeat receiver is whichever independent domain arrives first, sentinel-named or not.
- **R2 — Hardware-coupled services place with their hardware,** and the coupling is the placement decision: box-with-the-USB-stick, or a guest with passthrough if #555's seam has matured by then. Never alcyone (interactive, sleeps), never the Pi/Taygeta (sentinel purity, operator-recorded).
- **R3 — Uptime-expecting services fire the posture question before the purchase question.** The first service on electra with a real uptime expectation triggers the ADR-030 trigger-3 evaluation for electra (ring position last, kernel-update discipline, or stable channel), and only if the answer is "the posture can't stretch" does it escalate to R4. Cheap remedy before hardware remedy.
- **R4 — New always-on roles are assignments before purchases.** Maia (#638) exists in the target fleet as a named, role-open service-sink slot with no hardware in hand yet; a service that outgrows co-tenancy (via R3) or wants domain separation short of the Pi/Taygeta sentinel is a candidate *assignment* for it. What Maia is for is the operator's open decision — this rule only establishes that assignment precedes purchase in the escalation order.
- **R5 — Everything else lands on electra** at whatever tier the isolation sibling gives it. The default is boring by design.
- **R6 — Reconstitution trigger.** If ≥3 uptime-expecting services accumulate (a products wave), the dissolved category reconstitutes and the dedicated-products-host question reopens with evidence in hand — the 08:57 comment's shapes get re-weighed then, not before.

**Sequencing couplings (time-sensitive, so named here rather than deferred).** A first provision is the program's golden insertion point (operator, 09:26 comment lineage): TPM-sealed LUKS + a persist whitelist enrol for free at first provision, skipping the re-provision cost a retrofit budgets for — proven three times over since this note was drafted, not just argued: alcyone, alnair, and electra all shipped LUKS2 + `systemd-cryptenroll` TPM2 (Option A, #631/#557) and an ephemeral-root persist whitelist at first boot, not as a later retrofit. #557's remaining scope is correspondingly narrow — the encryption leg is done fleet-wide, and only the signing + measurement leg (Secure Boot / lanzaboote, PCR policy) is still open; the issue was re-scoped off its "metis first" framing on 2026-08-11 to match. metis has no rebuild to bundle anything into — it exits, and its hardware later returns as a fresh host outside this note's scope. The golden-insertion-point framing now applies forward: to Maia's first provision, to Taygeta's if the Pi is ever provisioned, and to the successor host that eventually replaces metis's hardware — each should enrol #557-class posture (whatever remains of it) and a persist whitelist at bring-up, the same free win the last three hosts already banked.

**The automation-plane flag (named, not designed).** If n8n is adopted, the fleet gains a second scheduler beside systemd timers/CI/#565 charters; before its first load-bearing automation, a one-paragraph boundary (which plane owns what class of job) needs recording, or the fleet grows two uncoordinated cron planes. That is a future small decision, attached here so it is not lost.

How the design meets the forces: P1 (R1, with the live violation named), P2 (R1/R4 keep functions off single points; nothing here makes electra a gate), P3 (R3 makes the cadence question explicit and cheap-first), P4 (R2), P5 (no rule reaches for capacity; R4 is about domains, not gigabytes), P6 (rules and triggers only; zero placements decided), P7 (every rule degrades: no Taygeta → R1's gap is recorded, not hypothetical, and is the live case; no Maia → R4 falls through to purchase-with-evidence; alcyone's arrival needed no rule change, since R2/R5 never depended on it as a plan).

## De-risk evidence

Verified against `main`, the fleet, and #387's current comment record, 2026-08-11:

- **The watcher-rule violation is live, and a deliberate relocation preserved it rather than fixing it.** `hosts/electra/default.nix:40-41` imports both `../../modules/nixos/unit-failure-notifier.nix` (the sender — "client from day one") and `../../modules/nixos/ntfy-server.nix` ("relocated here from metis, #688") on the same host. `lib/ntfy-endpoint.nix:16` single-sources `host = "electra"` for every consumer. So electra sends its own unit-failure alerts to its own ntfy instance — the same self-watching shape the 2026-07-07 draft found on metis, now on the host the comments called "always-on" instead of the one they called the re-role target. The relocating module's own header comment already names the residual, unprompted: `modules/nixos/unit-failure-notifier.nix:19-21` reads "Receiver is electra: an always-on, headless node (relocated from metis, #688), so the receiver's own failures are as blind as any other headless host's — #569's dead-man's layer is the answer to that residual." That comment is correct and honest, and it is also exactly R1's violation, recorded in the code and left unaddressed by the move that produced it — #688 relocated the receiver for a real, good reason (electra genuinely is always-on where metis was retiring) without this note's placement question being asked at the time. This is the note's strongest de-risk finding: this repo's own evidence shows "which box is always-on" and "R1's failure-domain rule" pointing at different hosts, and the fleet has now chosen the former twice.
- **The recent upstream-relay change does not touch this analysis.** Commit 12f9559 (#791, `modules/nixos/ntfy-server.nix`'s `upstream-base-url = "https://ntfy.sh"`) relays a content-free wake ping to ntfy.sh so the iOS app's APNs push fires; it is an outbound notification-delivery fix, sender-side, and electra is still the sender in this relationship. If electra is down there is no local alert to relay and no relay to trigger — the change makes a *reachable* electra's alerts reach the phone faster, it does nothing for an *unreachable* electra. Verified by reading the module: no inbound path, no redundant receiver, and no change to R1's exposure.
- **Darwin is no longer a separately-dark exception; it now compounds the same violation.** The 2026-07-07 draft noted "Darwin hosts have no failure notifier at all (#346)" as a partial mitigation — the Macs' silence didn't add to the watcher problem, it was just separately dark. #346 has since closed: `modules/darwin/launchd-failure-notifier.nix` exists and is imported at `hosts/neptune/default.nix:94`, pointed at the same `lib/ntfy-endpoint.nix` electra owns. So neptune's alerts also terminate at electra now — every host in the fleet, Linux and Darwin alike, funnels through the one instance R1 says shouldn't watch itself.
- **The comment chronology supporting Correction 1** is unchanged from 2026-07-07: the products-isolation case (08:57:25Z) predates the always-on/bursty split (09:26:26Z) on #387's own thread; the later comment materially changed the earlier one's premise. Operator-endorsed 2026-08-11 (Design, Correction 1).
- **The retirement premise is #387's own recorded decision, not this note's inference.** #387's current body (`gh issue view 387`) states: "Re-cut 2026-08-03 ... the operator has since decided metis retires from the fleet altogether ... not re-role into a homelab server ... and not relocate as an off-site anchor (#641's interim reframe, superseded by this decision)." This is the premise this note reworks onto, dated and current.
- **Maia (#638) is operator-recorded, not invented; Taygeta is a banked name with no live tracking issue.** Maia (#638, open) is the ADR-042 service-sink slot the target-fleet table in [fleet-ssh-identity.md](./fleet-ssh-identity.md) §target shape pencilled as "M720q (new, name TBD)" — that note's own target-fleet snapshot is dated 2026-07-07 and itself now stale (it still names jupiter/saturn/mercury); ADR-042 and #638 are the current-facts citation, this note uses the older note only to trace where the slot came from. Taygeta is the ADR-045 name banked for the Raspberry Pi (#547 comment, 2026-07-25), but #547 itself — the issue that would have onboarded it — closed not-planned on 2026-08-03 when its aarch64-CI rationale dissolved with nixos-vm's retirement (#634); its closing comment states "if the Pi ever lands, reintroducing the arch is a fresh intent framed against that reality." So R1/R4's Pi-sentinel dependency currently has no live tracking issue at all — materially weaker footing than "mooted, pending arrival," and worth flagging precisely because R1's remedy leans on it.
- **The encryption leg of #557 is fleet-wide fact, not a metis-first plan.** `hosts/alcyone/disko.nix`, `hosts/alnair/disko.nix`, and `hosts/electra/disko.nix` each implement "Option A (#631/#557): LUKS2 + systemd-cryptenroll TPM2" with `crypttabExtraOpts = [ "tpm2-device=auto" ]`; a repo-wide grep for `lanzaboote`/Secure-Boot signing modules under `modules/` returns nothing (this session). So #557's original "metis first" framing was stale twice over — encryption-at-rest already shipped on three other hosts first, and the only leg left open is signing + measurement; the issue was re-scoped accordingly on 2026-08-11.
- **electra's current always-on inventory** (census, this session, `hosts/electra/default.nix`): tailscale, wake-on-lan-emitter, unit-failure-notifier (client), ntfy-server (receiver), btrfs-scrub, ephemeral-root (enforced) — no docker, deliberately, gated on the open #637 role decision — a light, steady set, consistent with Correction 1's "steady, light co-tenants" premise, now measured on the host that actually carries the always-on role rather than the one the 2026-07-07 draft assumed would.

Unverified, stated rather than implied:

- **Kernel-update cadence on `nixos-unstable`** — unchanged: still qualitative, still unmeasured; R3's trigger does not depend on the exact rate.
- **HA's actual requirements** (USB specifics, tolerable blip duration, container-vs-native fitness) — unchanged: verified at its arrival, per R2/R3; everything said about HA here is from general knowledge and marked as such.
- **The dissolution lean's durability** — narrower now that it is endorsed rather than merely offered: it holds for the currently-named members (HA, n8n, keeper) as of 2026-08-11; a member with properties outside this analysis, or a wave (R6), revises it. That is what the trigger is for.

## Drawbacks

- **Rules-with-triggers rot if nothing watches them.** #562 (executable triggers) is unbuilt; until it exists, R3/R6's triggers live in prose and fire only if a human remembers. The mitigation is honest: the rules are few, and each is attached to an event (a service arriving) that forces the file open anyway — but a trigger missed at exactly such a moment is this design's failure mode.
- **The dissolution lean, now endorsed, could still be wrong cheaply or expensively.** Cheaply if products trickle in (R6 catches the wave); expensively if HA arrives *first and urgently* — the fleet would face its hardest placement (hardware + uptime + cadence) with the least accumulated evidence. The hedge is R3's posture-before-purchase ordering, which gives HA a workable interim (co-tenant with adjusted electra posture) while the real decision is made.
- **Deferring placements means the first mover still sets precedent under pressure — the exact failure the live alert-path violation demonstrates.** The rules reduce this (R5 gives a boring default; R1 names the exception class) but a rule set is only as good as the session that consults it — #688's relocation is the concrete evidence that a well-intentioned, correctly-executed change can still skip the rule if nothing forces the consultation.

## Rationale & alternatives

- **A0 — no rules; place each service at arrival.** The status quo that produced the self-watching alert path, and then preserved it through a relocation. Fails P1 today and P6's spirit (each arrival becomes an unframed debate). Rejected on demonstrated evidence, not taste.
- **A1 — select the products shape now.** Directly violates the operator's "open input, not a decision" instruction, and would decide against pending facts (Maia's role, #555's maturity, HA's real requirements). Rejected as both unfaithful and premature.
- **A2 — hypervisor-cloud placement (everything a guest on one always-on host, e.g. electra).** Answers placement by making it moot — one box hosts all. Re-couples every fate to that host (P1, P2), depends on the unbuilt #555 seam, and was rejected on the isolation axis for the same reasons (sibling note, A3). Rejected.
- **A3 — conditional rules + triggers (chosen).** The operator's own recorded style (frontrunner-not-resolved, watch conditions, decision-rules-when-triggers-fire — the inference-appliance comments are the house pattern); honours P6 by construction; converts the products question from "pick a shape" into "know which rule fires when." Its cost is Drawback 1 (prose triggers until #562); accepted knowingly. Doing nothing keeps A0's demonstrated failure mode, which #688's relocation showed is not self-correcting.

## Prior art

- **In-repo, primary:** #387's comments 3–6 are the arbitration this note integrates and corrects — the criticality classes, role map, and hardware direction are theirs; ADR-030 trigger-3 (uptime-critical workload → reconsider posture) is the operator's own pre-registered hook that R3 pulls; ADR-034's migration trigger (a stateful, local-only database) shapes what "stateful co-tenant" means for whichever service fires it — keeper (#386) is the worked example on record, not a queued service, since it needs retargeting off the retiring host before it can land at all; the inference-appliance comments model the lean+trigger+decision-rule form this note adopts wholesale.
- **In-repo, negative:** the alert path (unit-failure-notifier → its own host's ntfy — first on metis, then on electra after #688's relocation) is the worked example of placement-by-convenience; #569's dead-man framing ("the fleet's alerting detects failure but not absence") is the program-level statement of the same gap, and the relocating module's own header comment (`modules/nixos/unit-failure-notifier.nix:19-21`) now names the residual explicitly, in the code, rather than only in this note.
- **Industry:** "don't monitor from the monitored box" and "don't co-tenant the pager with the servers" are as old as operations; home-automation communities converge on the same split (HA near its radios, on hardware that reboots rarely) — corroborating R1/R2 from outside.

## Unresolved questions

- **Maia's (#638) role** — operator's decision, open; R4 only establishes assignment-before-purchase. Its hardware and timing are similarly unknown.
- **Whether a Pi/Taygeta sentinel is ever provisioned** — #547, its original vehicle, closed not-planned 2026-08-03, and nothing currently tracks bringing the hardware in. R1's stated remedy for the live violation depends on *some* independent domain arriving, sentinel-named or not; until one does, R1's gap stands as accepted, not closed.
- **electra's posture answer when R3 first fires** (ring position vs kernel discipline vs stable channel) — decided then, with ADR-030 amended per its own trigger; this note only guarantees the question is asked before hardware is bought.
- **Whether the dissolution lean survives contact with HA's real facts** — R2/R3 structure that decision; they do not pre-make it.
- **Where the rules live once accepted** — prose in an eventual ADR vs a small `lib/` datum the future #551 registry could assert against (each placed service declaring class + host + justifying rule); leans data-eventually, prose-first. ADR promotion is deferred (operator decision 4, recorded in #387 on 2026-08-11) — this note stands alone as the accepted-but-unpromoted record until that future work runs.
- Out of scope: the isolation tier of any service (sibling note); ingress/TLS and the backup mechanism (their own seams); #555's substrate; metis's own exit mechanics (#387's own #634-shaped decommission train, distinct from this note, which only carries the golden-insertion-point framing forward to future first-provisions); naming executions (#368).

## Future possibilities

- **#562 watches R3/R6's triggers** once executable triggers exist — this note is a live specimen of the parked-with-triggers pattern it would machine-read.
- **Taygeta's first tenant, if the Pi is ever provisioned,** is the alert-path fix (R1): a receiver off the watched domain, probably alongside #569's heartbeat layer — turning the recorded violation into the sentinel's founding purpose. Absent a Pi, any other genuinely independent domain (Maia, once assigned a role) discharges the same fix.
- **A placement stance, ADR-042-shaped,** once ≥2 services are placed: every hosted service declares its class, host, and the rule that put it there; drift (a watcher co-tenant with its target) fails eval. The set≠enforced closure for this axis.
- **metis's own exit** inherits nothing from Sequencing couplings above — metis has no rebuild to carry #557/#553-class posture forward into, because that golden insertion point already fired for alcyone, alnair, and electra at their own first provisions. What remains for the exit is disposition, not enrolment: keeper (#386) retargeted, #557 re-scoped or closed as overtaken, and the desktop/dev duties relocated per #387's own relocation list — all downstream of this note, in #387's own decommission train.
