# Noctalia v5 native theming — source-level evidence for a possible authority migration

Status: **research note, not a decision.** Captured 2026-07-25 from a source-level dive (AI subagent) into `noctalia-dev/noctalia` @ tag `v5.0.0-beta.4` = commit `4c2dcd0995f9c570c0ced95561bf5e4685e2ad1b`, immediately after the v5 shell migration landed (#644). Purpose: evidence for the operator's question of whether the Linux desktop's theming authority could migrate from the bespoke ADR-044 conductor to Noctalia's native engine (macOS explicitly allowed to diverge). The in-session assessment concluded **no migration at beta.4** — the load-bearing blocker is that v5 has no mechanism to make declared theme config authoritative (GUI/IPC theme picks persist to the settings.toml sidecar and shadow `config.toml`, with the theme keys bypassing even v5's own auto-erase path), compounded by beta churn and thin tests — while noting the engine now clears three of the four gaps that originally forced the bespoke layer (terminal fidelity, declarability, watcher semantics) and that a hybrid (the base16 catalogue as custom palettes, v5's engine as renderer, an OSC hook retained for open terminals) is the natural landing zone if it is ever revisited. No tracking issue was opened (operator call); this note is the standing evidence. Feeds ADR-044's context and any future theming-authority decision.

---

## 1. Colour sources & resolution pipeline

**Builtin palettes.** Exactly 10, in a `constexpr std::array<BuiltinPalette, 10>` (`src/theme/builtin_palettes.cpp:12`): Ayu, Catppuccin, Dracula, Eldritch, Gruvbox, Kanagawa, Noctalia, Nord, Rosé Pine, Tokyo-Night. Every palette carries **both** `.dark` and `.light` modes (`builtin_palettes.h:15-19`), each with a 16-colour UI `Palette` **and a full hand-written `TerminalPalette`** — normal + bright ANSI octets, fg/bg, selection, cursor (`fixed_palette.h:78-87`); 20 terminal blocks = 10 × 2 modes, all explicit. Expansion to the full token set happens via `expandBuiltinPalette` → `expandFixedPalettes` + `applyTerminalPalette` (`builtin_palettes.cpp:1121-1126`), synthesizing container/fixed/inverse tokens in HSL with WCAG binary-search contrast enforcement (4.5:1 / 3.0:1; `fixed_palette.cpp:204-361`, `contrast.cpp:33-67` — WCAG luminance, not CAM16).

**Wallpaper-derived.** A genuine vendored material-color-utilities C++ port (`src/theme/m3_schemes.cpp:1-12` includes MCU `hct.h`, `wu.h`). Image → resize to 112×112 ignoring aspect (`image_loader.cpp:18,277-280`; the resize is a byte-for-byte port of the Rust `image` crate's Triangle filter for M3 schemes) → Wu quantizer (128) → a deliberately **bug-for-bug matugen-faithful wsmeans fork** (`m3_schemes.cpp:40-81`) → matugen-faithful `Score` port (:226-305) → seed (fallback Google blue `0xff4285f4`). The quality knob is **`theme.wallpaper_scheme`** (default `"m3-content"`, `config_types.h:1419`; there is no `generationMethod` key): 5 MD3 variants (m3-tonal-spot/content/fruit-salad/rainbow/monochrome via MCU `DynamicScheme`, `m3_schemes.cpp:340-432`) + 5 custom HSL generators (vibrant/faithful/soft/dysfunctional/muted, `custom_schemes.cpp:487-543`). Terminal ANSI colours are **not quantized from the image** — both paths call `synthesizeTerminalPaletteTokens`, mapping role tokens → ANSI slots (red←error, green←primary, yellow←secondary, blue←tertiary, etc.; `fixed_palette.cpp:155-193`).

**Community palettes.** Catalog `https://api.noctalia.dev/palettes`, per-palette `…/palette/<name>` (`community_palettes.cpp:26-27,172-174`). Cached in the **state dir** (`<state>/community-palettes/<name>.json`; deliberate, comment :158-166), refreshed only on **md5 mismatch** against the catalog (`theme_service.cpp:486-490`). Offline: warning + cached metadata (`community_palettes.cpp:134-136`); stale cached palettes resolve immediately. A `dark.terminal` block is **required** — parse returns `nullopt` without it (`theme_service.cpp:175-179`); `light` optional, falls back to dark (:191).

**Custom palettes.** JSON files in `~/.config/noctalia/palettes/` (`custom_palettes.cpp:215-222`), same schema as community (dark mandatory incl. terminal; light falls back — resolution shares `parseCommunityPaletteJson`, `theme_service.cpp:465`). Noctalia can write them itself ("save wallpaper palette as custom", `custom_palettes.cpp:288-346`).

**Token set.** `src/theme/tokens.h:13-86`: **72 tokens** — `source_color`; primary/secondary/tertiary ×8 each (incl. fixed/fixed_dim variants) + `surface_tint`/`inverse_primary`; error ×4; the surface ladder (dim/bright + container lowest→highest); outline(_variant); shadow/scrim; inverse_surface pair; background pair; and **22 terminal tokens**.

**`resolveAndSet`** (`theme_service.cpp:457-550`): resolve mode (Auto → day/night scheduler) → source switch with **fallback-to-builtin on any failure** (:502-504; unknown builtin name → "Noctalia", :62-65) → post-transforms `applyPureBlackDark` (HCT tone-shift of the surface ramp; `palette_transform.cpp:20-59`) and `applyHighContrast` (:67-97), applied *after* the wallpaper memo cache → emission via callback (`src/app/application_services.cpp:506-526`) which drives template application + hooks, with an optional 400 ms lerp for the shell UI.

## 2. The template engine

**Builtin catalog: 20 ids** (`assets/templates/builtin.toml`): alacritty, btop, cava, emacs, foot, ghostty, gtk3, gtk4, helix, kcolorscheme, kitty, labwc, niri, hyprland, mango, qt, scroll, sway, starship, wezterm (19 asset dirs; the gtk dir serves gtk3+gtk4; the kde dir provides kcolorscheme). Each writes a noctalia-owned theme file, and — critically — **config-injection into the user's real config is the norm**: alacritty adds an import to `alacritty.toml` (`alacritty/apply.sh:16-35`); btop sets `color_theme` in `btop.conf` then `pkill -SIGUSR2 btop`; cava sets `[color] theme` + `pkill -USR1 cava`; foot **injects `include=…/themes/noctalia` under `[main]` in `foot.ini`, creating it if missing** (`foot/apply.sh:17-29`) with **no live-reload signal** (new windows only); ghostty rewrites `theme =` + `pkill -SIGUSR2 ghostty`; gtk appends `@import` to `gtk.css` — NixOS-aware, replacing read-only symlinks with a local file (`gtk/apply.sh:41-51`) — then runs the gsettings calls (§4); helix writes `helix/themes/noctalia.toml` with **no apply.sh, no reload**; kcolorscheme uses C++ `post_action = "kde-color-scheme"` (`template_engine.cpp:1527-1537`); kitty awk-rewrites `kitty.conf` (marker-block strip + ensure include) + `pkill -USR1 kitty`; **niri appends `include "noctalia.kdl"` to `config.kdl` if absent, creating `config.kdl` if missing** (`niri/apply.sh:29-48`), relying on niri's own config watch; qt writes qt5ct + qt6ct scheme files (array output) with no hook — manual selection required; starship discovers `STARSHIP_CONFIG` via systemd user env or **scanning `/proc/*/environ`** and splices a palette between markers (`starship/apply.sh:32-65`); wezterm edits `wezterm.lua` and `touch`es it; sway/scroll/labwc/mango/hyprland/emacs similar (hyprland probes lua-vs-conf via `hyprctl`). Scripts run via `/bin/sh -lc` (`src/core/process/process.cpp:910-914`). A Firefox theme ships separately via native messaging (`src/theme/firefox_theme/`).

**Community templates** (`community_templates.cpp`): catalog from `https://api.noctalia.dev/templates` (:31) into `<state>/community-templates/`, md5-validated, each with a `template.toml` processed like builtin.toml; synced at startup and on theme-config reload (`application_services.cpp:441-448`).

**User templates** (`config_schema.cpp:1006-1119`): `[theme.templates]` → `enable_builtin_templates` (default true), `builtin_ids` (**default empty ⇒ per-template opt-in**, `config_types.h:1404-1410`), `enable_community_templates`, `community_ids`, `custom_colors`, and `[theme.templates.user.<id>]` with `enabled`, `input_path`, `input_path_modes {dark,light}`, `output_path` (string or array), `output_path_dynamic` (shell command producing output lines), `compare_to`/`colors_to_compare` (CIELAB nearest → `{{closest_color}}`, `template_engine.cpp:507-524`), `pre_hook`/`post_hook`, `post_action` (only `kde-color-scheme`/`firefox-theme`), `index` (stable-sort order). `input_path_dynamic` exists in the engine but is **not exposed in the user schema**. `custom_colors` synthesizes full M3 tonal sets per named colour (:1357-1432). Syntax: `{{colors.<name>.<dark|light|default>.<format>}}`, matugen-style formats and pipe filters, `<* for/if *>` blocks (`template_engine.cpp:122-133, 235, 723-779`).

**Execution:** a dedicated worker thread with a single pending slot (`template_apply_service.cpp:137-151, 297-325`), triggered on every palette resolution; **dedup is input-equality** (palette + templates + mode + imagePath + schemeType, `sameInputs` :204-210) plus per-file **content-compare before write** (`template_engine.cpp:646-649`); a generation counter cancels superseded runs. IPC `templates-apply` force-reapplies (`template_apply_service.cpp:212-226`; wired `application_ipc.cpp:751`).

**Fully declarative? Yes.** All template config lives in the ordinary config schema; config layering (`config_service.cpp:486-527, 1457-1459`) merges all `*.toml` in the config dir alphabetically, then deep-merges the state-dir `settings.toml` sidecar last. Nothing template-related is GUI-only, and enabling templates via config.toml requires **no** settings.toml state (`example.toml:134-144` documents the declarative form). Caveats: a stale sidecar `builtin_ids` **replaces** config.toml's array wholesale; community templates need the network-fetched state cache; and the apply.sh scripts imperatively mutate target apps' configs — only gtk handles read-only symlinks, so e.g. niri's append to a home-manager-owned `config.kdl` would presumably fail (inferred from `niri/apply.sh:47`; not runtime-tested).

## 3. Selection & persistence

Two layers: hand-authored `~/.config/noctalia/*.toml`, and app-written `~/.local/state/noctalia/settings.toml`, placed in state "so it can still be written when the config dir is read-only (e.g. NixOS)" (`config_service.h:199-205`). **Sidecar wins** (`config_service.cpp:1457-1460`). GUI/IPC persist: `theme.mode`, `theme.source` + per-source key (`builtin`/`wallpaper_scheme`/`community_palette`/`custom_palette`; `config_overrides.cpp:904-961`), `pure_black_dark`, and the template toggles/id arrays (`settings_registry.cpp:793-838`). All the same keys are valid in config.toml (single schema, `config_types.h:1362-1425`) — pinnable, but only until shadowed.

**No pin/lock/managed mechanism exists** (grep for readonly/locked/managed: nothing). Nuances: the generic `setOverrides()` path auto-erases overrides that produce a config identical to the without-override result (`config_overrides.cpp:1643-1651, 1273-1306`) — re-picking config.toml's own value leaves the sidecar clean — **but `setThemeMode`/`setThemeColorScheme` bypass this** and always persist (:884-961). The only route back is the per-key "reset" button in the GUI (`settings_control_factory.cpp:164-178`) which erases the sidecar key. There is no option to disable persistence.

**`theme.mode = auto`**: `day_night_schedule::evaluate` computes solar sunrise/sunset from `[location]` lat/lon (IP-geolocated or manual); fixed HH:MM `sunset`/`sunrise` apply only when `custom_schedule = true` (`day_night_schedule.h:23-28`, `config_types.h:1245-1251`); a timer re-evaluates at min(next boundary, 1 min) (`theme_service.cpp:552-563`). Manually setting mode while on auto writes `theme.mode = "dark"|"light"` — a **permanent flip to manual**, not a temporary override (:307-329). IPC (`theme-mode-toggle/get/set`, `color-scheme-get/set`, `templates-apply`; `theme_service.cpp:660-715`) persists identically to the GUI. The offline `noctalia theme` CLI (`src/theme/cli.cpp`) renders palettes/templates without touching settings.toml.

## 4. Polarity & portal

The **gtk template's apply.sh is the sole freedesktop color-scheme writer**: `gsettings set org.gnome.desktop.interface color-scheme "prefer-$mode"` plus `gtk-theme adw-gtk3(-dark)` if installed, dconf fallback (`gtk/apply.sh:86-105`); it runs on every gtk3/gtk4 render, i.e. every palette/mode apply while enabled (`builtin.toml:112-121`). An `--appearance-only` flag exists but is never invoked from C++. **Nothing reads** `org.freedesktop.appearance` or portal Settings — confirmed by grep; all "portal" hits are process detection (`process.cpp:881-887`). Noctalia never follows an external polarity change. Mode flips re-render everything: `setThemeMode` → reload → `resolveAndSet` → `TemplateApplyService::apply`; `sameInputs()` includes mode, so a flip is never deduplicated, and `input_path_modes` picks the per-mode input at parse (`template_engine.cpp:1186-1195, 1284`).

## 5. Wallpaper coupling

Wallpaper change → single callback chain (`application_services.cpp:736-746`) → `ThemeService::onWallpaperChange()` regenerates only when `source == Wallpaper` (`theme_service.cpp:278-282`), memoized on (path, mtime, scheme) (`theme_service.h:53-73`). Per-monitor wallpapers are fully supported (`config_schema.cpp:744-750`), but **there is no `monitorForColors` analogue** — palette generation uses the **most recently applied** wallpaper (`getPaletteWallpaperPath`, `config_overrides.cpp:1847-1855`): last-set wins. Reverse coupling: **no per-scheme wallpaper pools**; the only linkage is *mode*-keyed `directory_light`/`directory_dark` pools, globally and per-monitor (`wallpaper_paths.cpp:6-11, 41-52`) — relevant to #648, which therefore needs repo-side glue under either theming authority.

## 6. Settings-UI surface

All in the C++ settings registry (`src/shell/settings/settings_registry.cpp`): mode segmented control (dark/light/auto, :432) with location/custom-schedule controls (:2293-2315); source picker (:437) with builtin swatch-preview picker, wallpaper-scheme picker (all 10 generators), community search-picker, custom search-picker (:187-232, 441-486); pure-black-dark toggle (:489); high-contrast toggle (:547-549); builtin- and community-template toggles + per-template grids (:786-842); "save wallpaper palette as custom" (`settings_window_scene.cpp:1700-1718`). **No GUI palette editor, no user-template editor, no contrast slider** — user templates and `custom_colors` are config-file-only.

## 7. Extensibility & maintenance

20 builtin catalog ids upstream plus Firefox. **Matugen compatibility is deliberate and deep**: identical placeholder/block syntax, matching format/filter sets, and the generator pipeline replicated "byte-for-byte" including matugen's bugs (`m3_schemes.cpp:31-153`); matugen templates should drop in largely verbatim (not runtime-tested). Tests are thin: `tests/scheme_test.cpp` and `tests/kde_color_scheme_test.cpp` only; **no template_engine unit test** — parity was validated by dev-machine comparison scripts (`tools/template-engine-compare-all.py`, `tools/palette-generator-analysis.py`). Docs: no in-tree docs dir; schema documented via commented `example.toml:120-144` — thin for template authors. Churn: near-zero TODOs in `src/theme`; active config-migration machinery (`config_migrations.cpp:153, 212`) shows the config surface still moving; the whole engine is a fresh v5 rewrite (of a legacy Python engine, per `tools/template-engine-compare-all.py`).

**Not verified:** runtime behaviour of any apply.sh (incl. gsettings propagation and the read-only `config.kdl` failure mode); api.noctalia.dev live catalog contents; vendored MCU sources not independently audited; full bodies of `custom_schemes.cpp` generators sampled, not exhaustively read; git churn history unavailable (shallow single-commit clone).
