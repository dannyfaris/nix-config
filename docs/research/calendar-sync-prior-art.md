# Conditional calendar sync (CalDAV hub-and-spoke) — prior art & viability, for #386

Status: **research note, not a decision.** Captured from a deep-research run (5 angles, 21 unique sources fetched, 102 claims extracted, top 25 adversarially verified at 3 votes each: 23 confirmed / 2 refuted, 8 budget-dropped) on 2026-08-03; run ID `wf_df6a51e7-6bc`. Provenance caveats: the operator requested Opus-model subagents, but the harness ran all agents on the session model (Fable 5) — the packaged deep-research workflow applies no per-agent model override; recorded for provenance, not as a quality caveat. Claims extracted from fetched sources but *not* adjudicated in the top-25 verification pass are explicitly marked **UNVERIFIED**. Ask: for the #386 design loop's fork 3 ruling (option C — Radicale hub as source of truth on electra + vdirsyncer transport + DavMail bridging M365 + a small custom rules/projection daemon for conditional routing and privacy-shaping), does prior art validate the shape, do the load-bearing 2026 claims hold, and what failure modes must the design absorb? Feeds the calendar-sync design note (De-risk evidence) and #386. Survey-bounded — §6 lists what the run did *not* establish.

## 1. Verdict

**The architecture is viable, with one high-risk leg and several checks still open.** The shape has direct (if minimal) practitioner prior art, and no existing tool fills the custom daemon's seam — bidirectional, CalDAV-native, rule-driven projection between staging and canonical collections — so the daemon remains justified. The Google leg is validated end-to-end. The M365/DavMail leg is the architecture's weak plank on three independent grounds: a forced mid-flight protocol migration (EWS blocked from 2026-10-01), a maintainer-labelled-beta Graph backend whose recurrence handling was still being repaired in June 2026, and the transport layer's own documentation warning of data-loss-class unreliability against Exchange — arguing for treating that leg as read-mostly until proven. Two findings cut against earlier session assumptions: the claim that keeper.sh *lacks* conditional/privacy shaping was refuted (its capability is unresolved either way, so the "keeper rejected" rationale needs a direct capability check), and vdirsyncer's author is building a successor (pimsync), making vdirsyncer's maintenance trajectory a live selection question. Radicale's property fidelity and iOS compatibility produced **no surviving claims** — they are unverified assumptions, not validated facts.

## 2. Prior art for the shape (research question 1)

**The hub-and-spoke half exists in the wild, small-scale.** A homelab operator built Radicale-hub + vdirsyncer-transport in early 2023, merging multiple calendar sources into one personal CalDAV collection shared with family — cron-driven (discover hourly, sync 2-hourly) inside a container, htpasswd auth, Radicale's default filesystem storage, client devices pointed at the hub seeing the merged calendars, with no reported sync loops, RRULE corruption, or UID conflicts, and DAVx5 (Android) confirmed working — though nothing on iOS or conditional filtering (**UNVERIFIED** — extracted from [terramoto.xyz](https://terramoto.xyz/posts/merging-calendars-from-multiple-sources/), not in the adjudicated top-25).

**Keeper.sh is the closest packaged analogue, but a different hub.** It is real, self-hostable, actively maintained prior art for hub-and-spoke calendar aggregation (Google, Outlook/O365, iCloud, Fastmail, CalDAV, ICS sources → one or many destinations), but its hub is its own PostgreSQL-backed application, not a CalDAV server, and its stated goal is time-slot/busy alignment (3-0). Its self-hosting footprint is substantially heavier than the Radicale+vdirsyncer stack — PostgreSQL, Redis, multiple microservices — and its README documents no RRULE handling or conflict resolution (**UNVERIFIED** detail). Critically, the claim that keeper has *no* conditional routing or busy-only privacy shaping was **refuted 0-3** — the positive capability was never verified either, so whether keeper partially obviates the custom daemon is an open question (§6), not a settled rejection.

**The filter/transform half exists too, but one-way.** ical-filter-proxy (Go, MIT, active through 2026-07-21, Nix-deployable) applies ordered per-calendar match/remove/transform rules — but strictly ICS-feed-in → read-only-ICS-feed-out over HTTP(S), no CalDAV input/output, no write-back (3-0 ×3 merged claims). It could *read* a Radicale collection via an ICS GET, but has no CalDAV PUT path, so it cannot fill the staging→canonical projection seam. Useful as design prior art for the daemon's rule schema, not as a replacement.

**Conclusion: nobody has published the full shape** — hub + pairwise transport + *bidirectional conditional* projection. The two halves exist separately; the seam between them is the genuinely novel part, which is exactly where the custom daemon sits.

## 3. The Google leg — validated (research question 2a)

- The CalDAV v2 endpoint (`apidata.googleusercontent.com/caldav/v2/`) is documented live and supported, page last updated 2026-05-01; only the ancient `google.com/calendar/dav` endpoint is deprecated (3-0). Caveat: Google's Calendar API release notes contain no CalDAV entries at all (a claim citing them as corroboration was refuted 0-3), so continuity rests on the guide page's freshness plus the absence of any shutdown announcement — Google makes no formal support commitment.
- Access mandates HTTPS + OAuth 2.0 — basic auth returns 401, and the app-password loophole died with the less-secure-apps shutdown (2025-03-14). The operator must self-register an OAuth client in Google Cloud Console (project → enable CalDAV API → Desktop-application Client ID/Secret); vdirsyncer cannot ship shared credentials under Google's ToS (3-0 ×3).
- vdirsyncer's Google OAuth breakage is historical: the OOB flow Google barred in 2022 was replaced with a loopback `127.0.0.1` redirect in 0.19.0 (PR #985), support maintained through at least 0.21.0 (3-0 ×3). Residual friction directly relevant to electra: the loopback flow assumes a local browser, so headless hosts report auth difficulty — token bootstrap will need a one-time forwarded/desktop flow with the token cache then persisted on electra.
- Corroborating signal: pimsync — by the vdirsyncer author — was being designed against Google CalDAV v2 as of March 2025, indicating both endpoint life and where pimutils maintenance energy is going (**UNVERIFIED**).

## 4. The M365 leg — highest risk (research question 2b)

- **Forced protocol migration, tight timing.** Microsoft blocks EWS in Exchange Online tenant-by-tenant from **2026-10-01** (under two months out); tenants keeping it temporarily must configure an `EWSAllowedAppIDs` allowlist **before end of August 2026**; permanent removal 2027-04-01 (3-0 ×3). This is the maintainer's stated motivation for DavMail's Graph backend.
- **DavMail is healthy and converging on Graph, but the backend is beta.** Four 2026 releases (6.6.0–6.8.1, latest ~5 weeks old at capture); Graph experimental since 6.4.0, first GUI-selectable in 6.8.0 (June 2026) with mode/auth config split; O365 modern auth (OAuth2+MFA) since 5.0.0 (3-0 ×5). The tracking issue still carries "current state is beta, don't use it for production mailbox access (yet)" (reconfirmed 2026-06); the calendar path is marked DONE in the implementation checklist (3-0 ×3).
- **Recurrence fidelity is the least-settled part of that beta.** 6.8.0 shipped extensive Graph-tagged recurring-event repairs — exdate/exception ordering, RECURRENCE-ID adjustment for Graph's always-UTC originalStart, UNTIL-format handling, numbered recurrence — i.e. RRULE exception structures were still being actively fixed in June 2026, directly implicating the corruption failure mode this architecture must avoid (3-0, single-source).
- **Unattended auth is constrained.** Microsoft's enforced MFA number matching killed fully-transparent Authenticator-push auth; DavMail's native TOTP support (`davmail.oauth.totpSecret`, 6.7.0) restores an unattended path, with the maintainer still recommending interactive auth as most generic (3-0 ×2). For always-on electra, TOTP-as-factor is the viable shape — with the TOTP secret then living in sops.
- **The transport layer's own docs flag this pairing.** vdirsyncer's DavMail tutorial: success "may wildly vary… weird errors of all sorts (including data-loss)"; corroborated by issue #1140 (0.19.3 + DavMail + O365 producing 700+ duplicates of one deleted invite) and #144 (duplicate-item storms from hrefs differing only in case) (3-0).
- **Net implication:** the M365 leg should enter the design as one-way/read-mostly (M365 → hub) or heavily staged-and-validated, not trusted bidirectional sync — and the operator's work tenant must be checked for whether it permits the required Entra app registration at all (§6).

## 5. Failure modes and mitigations (research question 3)

- **Loop/echo/duplicate prevention has a proven cheap pattern:** keeper.sh marks every event it creates with a provenance marker — a `@keeper.sh` UID suffix, or a category on platforms disallowing custom UIDs (Outlook) — and drives push/delete/stale-cleanup off the marker. Its tracker shows zero loop/echo-storm issues; one open edge case (moves can duplicate, #124) (3-0). Directly reusable in the projection daemon.
- **False conflicts from raw-text comparison:** vdirsyncer compares item text, not normalised iCalendar structure, so a client merely reordering VTIMEZONE components triggers sync conflicts (**UNVERIFIED**, vdirsyncer #1092). The daemon should normalise before diffing; expect occasional vdirsyncer conflicts of this class.
- **Clients diverge on recurrence exceptions:** many create `STATUS:CANCELLED` exception overrides instead of `EXDATE` on the master when deleting single instances (**UNVERIFIED**, DAVx5 FAQ) — the daemon's rule engine must treat both as "instance removed".
- **Radicale rejects malformed real-world data:** a 2026-01 test found Radicale refusing an .ics import containing Microsoft-originated updated meeting invitations until they were hand-deleted (**UNVERIFIED**, neilzone.co.uk) — bearing directly on the DavMail/M365 → hub leg; the staging collection should tolerate-and-quarantine rather than assume clean input.
- **Apple-client discovery against Radicale is quirky but solvable:** Apple Calendar scopes discovery requests to the username path, which can fail rights rules that Thunderbird's requests pass; resolved empirically by pointing the client at the collection root, and manual full-URL setup is confirmed working as of July 2025 (**UNVERIFIED**, Radicale discussion #1442) — macOS evidence, adjacent to (not proof of) the iOS story.
- **Radicale has no sharing granularity** as of 3.5.3 — collection sharing is a symlink workaround granting full mutual read-write (**UNVERIFIED**, neilzone.co.uk). Single-operator use is unaffected; relevant only if the hub ever serves more than one person.

## 6. What the run did *not* establish — live de-risk items

The following load-bearing checks produced **no surviving claims** and remain assumptions:

1. **Radicale fidelity** — verbatim preservation of arbitrary `X-` properties and RRULE/RECURRENCE-ID structures on PUT/GET round-trips. Empirically testable locally; should be a stage-4 probe.
2. **iOS Calendar against Radicale over Tailscale Serve HTTPS** — `.well-known` discovery, account setup, reliable read-write sync. Only macOS-adjacent evidence surfaced (§5). Needs a live probe.
3. **vdirsyncer's 2026 maintenance trajectory vs pimsync** — whether vdirsyncer remains the right transport pick or the design should track its successor; and whether the absence of per-item transform hooks (assumed, motivating the staging/canonical split) holds in current releases. Selection-grade check.
4. **keeper.sh's actual conditional/privacy-shaping capability** — the "it can't" claim was refuted; a direct feature check decides whether keeper partially overlaps the daemon or the rejection stands.
5. **The operator's M365 tenant posture** — whether it permits the Entra app registration DavMail needs (work tenants often restrict this); decisive for the M365 leg's feasibility regardless of DavMail's health.

## 7. Refuted claims

- "Keeper.sh's sync engine is content-agnostic mirroring only — no conditional routing, selective sync, transformation, or busy-only shaping" — **0-3**; the README does not support the negative claim (nor was the positive verified).
- "Google's Calendar API release notes corroborate CalDAV v2 continuity" — **0-3**; the release notes contain no CalDAV entries whatsoever, in either direction.
