# CI workflow — per-knob rationale

The operational companion to [ADR-025](./decisions/ADR-025-ci-in-flake.md). ADR-025 records the *decision* — CI is flake-defined, every check is a flake output, a thin GitHub Actions matrix runs `nix flake check`. This doc is the reading-guide to the resulting `.github/workflows/ci.yaml`: the per-knob *why* a maintainer wants when editing that file, without re-deriving it inline. Living doc — it tracks `ci.yaml` as runners, cache tuning, and action pins evolve, the way `docs/desktop/<tool>.md` tracks the desktop modules.

The split, so neither place restates the other: **ADR-025 owns the framework decision and the dated history** (the cache saga #218→#228, the macos-15 / Darwin-matrix addition, the SHA-pinning trigger). **This doc owns the standing operational mechanics** — the things you need to understand the file, not the story of how each was found. Where ADR-025 (or another ADR) owns the deeper rationale, this doc points rather than repeats. `ci.yaml` itself carries only a one-to-three-line "what breaks if you change this" at each knob plus a pointer here.

## Display name and branch protection

The job sets an explicit `name: flake-check (${{ matrix.arch }})`. This is load-bearing, not cosmetic. Branch protection on `main` requires specific status-check *names* (`flake-check (x86_64-linux)`, `flake-check (aarch64-darwin)`). Without the explicit `name:`, GitHub auto-generates the check name from *every* matrix dimension — including the `runner:` key introduced by the `include:` block — yielding e.g. `flake-check (x86_64-linux, ubuntu-24.04)`, which never matches the protection rule, so the gate silently never applies. Keep the `name:` and keep it keyed on `matrix.arch` alone.

The required-checks set is configured out-of-band on GitHub (a ruleset), recorded in ADR-025 §Implementation and its §History. It is the two `flake-check (<arch>)` contexts **plus `gitleaks`** — so a secret-leaking PR can no longer auto-merge green. The `gitleaks` context is the gitleaks job's explicit `name:`; keep that name stable, since the ruleset matches on it. Adding a required check is **order-sensitive**: push the workflow so a run reports the context *first*, then add it to the ruleset — a context required before any run has reported it shows as "Expected — waiting" and blocks every PR indefinitely. If you add or rename a matrix arch (or the gitleaks job), update the ruleset in the same change or the new check won't gate (and a renamed one will leave an unmatchable required check blocking every PR).

The required-context set is **deliberately unchanged** by the docs-only short-circuit (§"Docs-only short-circuit"): name stability *is* the mechanism there — the job and its matrix always run and always report both contexts, only the command they run changes.

## Permissions

Pinned to the minimum (whitelist > blanket, per [CLAUDE.md](../CLAUDE.md)):

- `contents: read` — `actions/checkout` clones the repo; Nix fetches public flake inputs.
- `actions: write` — `cache-nix-action`'s `purge-primary-key: always` flow calls `DELETE /repos/.../actions/caches` to evict the existing entry before resaving. Without this scope that call returns **403 `Resource not accessible by integration`** and the resave is silently skipped, so the push-to-main refresh never happens. The scope is exercised on push-to-main runs only: a PR run's delete is ref-scoped away from the cache, so with the scope granted it returns **404** — a scoping symptom, not a permissions one; the mechanism is in §Cache. The post-save LRU sweep (`purge-prefixes`) needs the same scope and inherits the same scoping: functional on push-to-main, inert on PR runs.

The explicit pin matters because the GitHub default token grants more (`pull-requests: write`, `issues: write`, …) than this workflow needs. The dated story of how the missing `actions: write` scope surfaced is in ADR-025 §History (2026-06-04).

## Runners

The matrix pins concrete runner labels via `include:` rather than `*-latest`:

- `ubuntu-24.04` (x86_64-linux), `macos-15` (aarch64-darwin).
- `macos-15` is pinned rather than `macos-latest` — the floating label moves under us (it migrated to macos-15 in Aug 2025), which would silently change the build environment. The choice of the standard label over the metered `-large` / `-xlarge` / `-intel` variants, and the billing reasoning behind it, are in ADR-025 §History (PR #218) — not repeated here.
- `aarch64-darwin` matches the real arch of the fleet's Darwin host (neptune) — no Rosetta cross-arch surprises.

`nix flake check` on the macOS runner realises the Darwin host derivation (`flake.checks.aarch64-darwin.host-neptune`) but does **not** run nix-darwin activation — no `brew bundle`, `mas install`, `launchctl load`, or admin prompts fire at build time. CI is therefore side-effect-free on Darwin. The decision to add the Darwin matrix entry, and its cold-cache cost history, are in ADR-025 §History (2026-06-04).

Actions are SHA-pinned with a trailing `# vN` comment; the rationale and the trigger that prompted it are in ADR-025 §History (2026-06-05). Refresh a pin when you want a newer release; the trailing tag comment is the human-readable anchor.

## Docs-only short-circuit

A pull request that touches nothing but documentation still has to satisfy every required check, but it does not have to rebuild every host closure to do it. The `changed` step diffs the PR against the base branch's **current tip** — `git diff --no-renames --name-only "origin/$GITHUB_BASE_REF"...HEAD` — and sets one output, `code`. The basis is deliberately not the frozen `pull_request.base.sha`: that pointer is captured when the PR is opened and never advances, so once `main` moves the diff sweeps in every commit landed since and the short-circuit stops firing (#703). On a `pull_request` event `HEAD` is the merge ref — the PR head already merged into some base tip — so the three-dot merge-base resolves to whichever base tip GitHub merged in, and the diff is exactly the PR's own changes; a stale merge ref therefore degrades to "diffed against a slightly older base", never to a wrong file set. `origin/<base>` is present in the clone because `fetch-depth: 0` makes `actions/checkout` fetch with the all-heads refspec (`+refs/heads/*:refs/remotes/origin/*`) — that, not the depth as such, is what the checkout setting buys here. When every changed path is in the skippable whitelist, `code=false` and the job builds the flake's `checks-without-hosts` package — every check except the per-host `system.build.toplevel` builds — and nothing else. Otherwise `code=true` and the job runs the full `nix flake check` exactly as before.

**The cheap leg carries no `nix flake check --no-build` pre-step.** It opened with one, for flake-output schema validity, and that command cannot run here. `nix flake check` evaluates every host configuration, and Stylix's palette engine — the `base16.nix` flake input (`SenchoPens/base16.nix`), not a file inside Stylix — reads a scheme YAML out of the `base16-schemes` store path at *eval* time, which forces that path's context to be realised. `--no-build` forbids exactly that realisation, so evaluation dies with `error: path '…base16-schemes….drv' is not valid`. This is a property of *this leg*, not of the repo or of `--no-build` generally: the docs-only path deliberately skips the cache step (see §Cache) and so runs against a cold store where the path is absent. Where it has already been realised — a warm store, an operator's machine — the same read succeeds, which is why the local `--no-build` advice in [docs/workflow.md](./workflow.md) is unaffected. The full path never trips it either, because builds are permitted there.

**Dropping the pre-step loses nothing this leg needed.** A docs-only diff changes no Nix *expression*, so the flake's output *schema* — the only thing the pre-step validated — is unchanged by construction. The doc paths Nix genuinely does read are a separate matter and are gated by `checks-without-hosts` itself rather than by any schema pass: `docs/desktop/keybinds.md` via the `keybinds-table` check, `docs/design/*.md` via `design-note-structure`, and `CLAUDE.md` via `host-census`, all covered below under "No doc carve-outs are needed". Host evaluation is not lost either — the `stances-*` checks inside the cheap set force a full evaluation of every host configuration.

**The whitelist, and its direction.** Skippable: `docs/**/*.md`, root-level `*.md`, `.github/*.md`, and `LICENSE` — with `docs/design/_template.md` explicitly excluded, since the design-note lint reads the template as its prompt source and an edit there changes what that gate accepts. Everything else forces the full run: non-markdown assets under `docs/`, anything under `.github/workflows/`, and every path outside those trees. The match is a whitelist, so the fail-safe direction is *toward* building: an unrecognised path, an empty diff, a missing `origin/<base>`, or a failed `git diff` all yield `code=true`. A mixed docs-and-code PR is handled by construction — one unmatched path is enough to force the full run. Widening the whitelist is one regex edit; a wrongly-skipped build is a broken `main`.

**Nothing is ever skipped — only substituted.** The job always runs, its matrix always expands, and both `flake-check (<arch>)` check runs always report under their existing names (see §"Display name and branch protection"). This is the whole mechanism: GitHub leaves a *skipped* required check in `expected` forever, which under squash auto-merge is a silent, permanent hang, and it is why `paths:` / `paths-ignore:` on this workflow, a job-level `if:`, and a name-collided stub workflow are all unusable here. Substituting the command dodges that class entirely rather than managing it.

**`push: main` never short-circuits.** The `changed` step is gated on `github.event_name == 'pull_request'`, so a push to `main` leaves `code` unset and falls through to the full check. Main pushes are what seed the cache prefix every PR branch restores from, and they are the last full-fleet build before a commit is on `main`.

**No doc carve-outs are needed.** Documentation that legitimately gates code — `docs/desktop/keybinds.md` (diffed by the top-level `keybinds-table` check), `docs/design/*.md` (the `design-note-structure` lint, one of the hooks inside the `pre-commit` check), `CLAUDE.md` (the `host-census` lint, another hook inside that same check), and any doc lint added later (ADR-037 §2 contemplates cited-path and link checks) — is still fully covered, because `checks-without-hosts` is derived by exclusion and so contains both the `keybinds-table` check and the `pre-commit` check that carries the lint hooks. A path-filter design would have to enumerate and maintain those exceptions; this one does not have any.

**Policy stays in the flake.** `checks-without-hosts` is a flake output (`parts/checks.nix`), derived by *excluding* the `host-*` prefix rather than by listing what to include, so a check added later is picked up with nothing to remember. The YAML says only "build the cheap set", and `nix build .#checks-without-hosts` reproduces the docs-only CI path locally — the same property ADR-025 §Rationale claims for `nix flake check`.

**Expect minutes, not zero.** The leg still pays runner provisioning, checkout, `install-nix-action`, the flake-input fetch, a full evaluation of every host configuration (the `stances-*` checks force it), and a cold re-substitution of the whole `checks-without-hosts` closure from `cache.nixos.org`, since the cache step is skipped on this path (restore as well as save, see §Cache). The saving is the host closure *builds*, which is the expensive half on x86_64-linux; budget a few minutes per leg rather than near-zero.

## The pre-commit / CI boundary

What runs at `git commit` versus what only CI can run — a reading-guide to the split that `parts/checks.nix` encodes but does not narrate. The decision *to lift every hook into the flake* is [ADR-025](./decisions/ADR-025-ci-in-flake.md) §Rationale ("every check CI runs is a flake output"); this section is the standing map of where each class lands, not that decision.

**Commit-time-only: nothing.** No check runs at commit-time that CI does not also run. That is deliberate and total — `git-hooks.nix` lifts every hook in `pre-commit.settings.hooks` up into `checks.<system>.pre-commit`, so the commit-time set is a strict subset of the CI set, never a superset. There is no "local-only" guard to forget to mirror.

**Shared — runs at commit-time *and* in CI (one derivation, lifted):** the pre-commit hook set. Described by class, not by count, because the set grows (#435 adds a dprint formatter to exactly this surface): the packaged linters (statix, deadnix, shellcheck, actionlint); the treefmt formatter, which reuses the single `parts/formatter.nix` wrapper (nixfmt + shfmt) rather than re-declaring the tools; and the repo's own custom structural lints — `hardware-config-banner`, `shared-purity`, `bundle-purity`, `design-note-structure`, `host-census`, `case-collisions` — several paired with a self-test hook (`test-shared-purity`, `test-design-note-structure`, `test-host-census`) that exercises the linter's negative paths so a lint that silently starts passing everything is itself caught. Every one of these runs identically at `git commit` and under `nix flake check`; there is one source and one code path.

**CI-only, and irreducibly so:** two classes the commit-time set structurally cannot carry.

- **The per-host `system.build.toplevel` builds** (`host-alcyone`, `host-alnair`, …, `host-neptune`). These cannot run on one dev box: the fleet spans `x86_64-linux` and `aarch64-darwin`, so no single machine can build the whole matrix, and each toplevel is a genuine multi-minute closure build (the desktop hosts carry source-only builds like noctalia). A commit-time hook that built them would tax every commit with the exact work CI exists to absorb.
- **The eval-only checks** — `stances-*`, `lib-*`, `hosts-registration`, `keybind-collisions{,-darwin}`, `keybind-registry-shape`, `keybinds-table`. These *look* cheap enough to shift left, and the `lib-*`/`keybind-*`/`keybinds-table` ones nearly are (pure registry eval, or a gawk region-diff). But the `stances-*` class is not: `mkStanceCheck` is called with `self.nixosConfigurations.<host>.config` (`parts/checks.nix` `flake.checks.x86_64-linux.stances-*`), so forcing that check forces a full evaluation of the entire host configuration — the same eval the toplevel build front-loads. Shifting it to a commit-time hook would pay that per-host eval on every commit, for a class with no attested round-trip cost — the ceremony [ADR-032](./decisions/ADR-032-proportionate-enforcement-and-rationale.md) rules out (mechanism sized to attested severity).

**Why CI cannot be fully replaced by commit-time hooks.** Three reasons compound: the cross-arch matrix (above) means no one box can stand in for the fleet; `git commit --no-verify` is a sanctioned escape hatch, so any hook is best-effort and can never *guarantee* it ran; and the hooks are opt-in per clone (installed by the dev-shell's `shellHook`), not enforced on the repo. The gate that actually blocks a merge is not a hook at all — it is GitHub's branch-protection ruleset and its required contexts (§"Display name and branch protection").

**The cloud-session complement.** A nix-less cloud container has neither `nix` nor the linters, so the commit-time set is unavailable there. `scripts/fetch-lint-toolchain.sh` (#722) closes that gap for the *packaged-linter* class — it fetches statix, deadnix, shellcheck, actionlint, nixfmt and shfmt pinned to the flake's nixpkgs so a container gets the same verdicts locally; the story is [docs/design/cloud-session-lint-toolchain.md](./design/cloud-session-lint-toolchain.md). One caveat lives there: the custom lints are already bash-only and run nix-less, save `bundle-purity`, which needs `nix-instantiate` for its AST-parse and so is the lone hook the cloud-session path cannot reproduce.

## Substituters

The installer (`cachix/install-nix-action`) gets `extra_nix_config`:

- `accept-flake-config = false` carries the whitelist-over-blanket stance from `modules/shared/nix-daemon.nix` into CI — a transitive input's `nixConfig` block can't silently add a substituter or change settings on the runner. ADR-025 §Rationale owns this decision.
- No niri substituter is needed. Since #763 niri comes from nixpkgs (`programs.niri.package = pkgs.niri`), so `cache.nixos.org` serves it like any other package; the `niri.cachix.org` whitelist that mirrored `modules/nixos/niri.nix` retired with the migration off `sodiboo/niri-flake`. The flake module still ships a default-on `cache.enable`, which `niri.nix` keeps pinned to `false` so the fork cannot re-add its own.

## GitHub fetch token

Nix authenticates *every* github.com input fetch with the `access-tokens` line `install-nix-action` writes into the runner's nix.conf, so both nix-evaluating workflows pass it `github_access_token: ${{ secrets.GITHUB_TOKEN }}`. Every input this flake takes is public, so the token is not buying authorisation — it is buying rate limit: an authenticated token gets GitHub's per-repository hourly budget, an unauthenticated runner shares the anonymous per-IP one with every other job on the Actions pool, and a full eval resolves the whole lockfile (~45 nodes) on each matrix leg. Dropping the parameter would leave nix.conf without the line and put every fetch on the anonymous limit.

It is deliberately not `GH_PAT_FLAKE_LOCK` — that one is scoped to *this* repo with write permissions for PR-opening in `flake-lock.yaml` and is a different job's token; one token per job, each with the minimum its job needs (whitelist > blanket). Should a private input ever land here again, `GITHUB_TOKEN` is the one thing that cannot serve it (scoped to this repo alone, 404 on any other private repo) and the fetch would need its own read-only fine-grained PAT wired in at this same spot, plus a user-scoped `access-tokens` line on every machine that evaluates the flake.

## Cache

`cache-nix-action` provides `actions/cache`-shaped storage for build **outputs**. It is **not** a substituter and was orthogonal to the since-retired `niri.cachix.org` trust lines — it amortises the non-niri half of the desktop closure (Quickshell, Qt6, matugen, DMS, xwayland-satellite, foot, transitive deps) that a fresh runner would otherwise rebuild every cold run. It is a post-ADR-025 addition (under `#61`, an ADR-028 follow-up — ADR-025 §23 deferred the binary-cache question and CI v1 ran cache-less), not a foundational CI-v1 decision; the dated sizing/tuning history is in ADR-025 §History.

**Why this and not Cachix / FlakeHub / Attic.** Those are larger trust or operational delegations than a one-operator / few-host project warrants today (a substituter is a signing-key trust root; Attic is a service to run). `cache-nix-action` is plain `actions/cache` storage with no new trust root. Revisit only if hit-rate stays below ~60% over a month, or a second major source-built dependency lands (the `#61` "triggers to revisit"). That second trigger fired on 2026-08-02 — `noctalia` is the second such dependency — and the follow-up it points at is #418; it is recorded here rather than silently satisfied below.

**Key semantics.** The primary key is `nix-<os>-<arch>-<flake.lock hash>`, so a lockfile bump invalidates cleanly. PR branches restore from the `<os>-<arch>` prefix seeded on `main`; the squash-auto-merge flow reseeds after each PR lands — and that is the *only* reseeding path, since PR runs are restore-only (see **The refresh happens on push-to-main runs only** below).

**Cache sweep.** Before saving, `cache-nix-action` runs `nix store gc --max (storeSize − gc-max-store-size)` against the whole store. Nix can only delete *dead* paths, and `nix flake check` registers no GC roots — so without intervention every path CI just built is dead, and nix deletes in `readdir()` order with no regard for size, recency, or value. The x86_64 leg's store is ~19 GB against a 5G ceiling, so 77% of it goes on every save. That draw is arbitrary but *deterministic* for a given store, which is why `noctalia-5.0.0` died every time rather than in some fraction of runs. That one path is a ~23-minute C++ build with no binary cache upstream, no substituter to whitelist, and therefore the single largest item in the leg's runtime (#712). The `root the unsubstitutable outputs` step fixes it by building `packages.<system>.ci-gc-root` with `--out-link` — a link farm over the leg's unsubstitutable set, which on x86_64 is two entries — `noctalia`, taken from the flake attribute the desktop hosts themselves read, and `nvidia-settings`, routed through alcyone's own `hardware.nvidia.package` so the rooted path is the derivation alcyone builds rather than a parallel one (kernel-coupled via `boot.kernelPackages`; ~90 s warm rebuild, #721) — and on aarch64-darwin is nothing at all. Rooting every check output was designed first and measured out: the union floors at 15.93 GB of narSize, ~8 GB compressed, which alongside the other legs' entries (three of them at that measurement) puts the pool at ~11.8 GB against its 10 GB cap (metis, 2026-08-02). The pool is only worth spending on bytes that no substituter will serve; everything else — the four host toplevels, firefox, thunderbird, the firmware bulk — is deliberately left to be re-fetched from `cache.nixos.org`, which costs about the same per byte as restoring it from GitHub. (An earlier revision listed nvidia here as substitutable; that was factually wrong — `nvidia-settings` 404s on `cache.nixos.org`, measured on metis 2026-08-03, and is now rooted.) That trade is real and shows up in the warm run: the swept substitutable bulk is re-substituted every time, measured at ~94 s and expected somewhat higher under a targeted floor. It is bought back against ~23½ minutes. What the sweep takes is then everything the root does not reach. It does *not* take `.drv` files or input sources; `keep-derivations` is on by default, so a live output keeps the derivation that produced it, and that derivation keeps its own inputs in turn. The sweep's floor is therefore the rooted runtime closure **together with** its derivation graph and the sources feeding that graph, not the runtime closure alone — noctalia's runtime closure is 2.47 GB, and its real floor 3.69 GB. A red run is safe by construction: the pinned action declares `post-if: "success()"` (`action.yml:192` at `7df957e`), so a failed job runs no purge, no GC and no save whatever, and `main`'s entry is left exactly as it was.

**The ceilings are unchanged, and that is a decision.** `gc-max-store-size-linux: 5G` and `gc-max-store-size-macos: 8G` stay exactly as they were. Rooting changes what a ceiling *can* reach, not what it *is*: a rooted path is immune to `--max-freed` at any value, and every unrooted path — which is nearly the whole store on every leg — is still evicted in directory-read order exactly as before. On aarch64-darwin nothing is rooted at all, so its ceiling remains a pure eviction dial and its current value is what empirically holds a 2m35s warm check. On x86_64-linux the 5G budget runs out at ~13.94 GB freed, before it reaches the rooted floor — noctalia's 3.69 GB plus nvidia-settings' deriver-inclusive ≈4.24 GB (measured on metis 2026-08-03), ≈7.9 GB combined — so the floor never binds and its exact value is not load-bearing. Lower would sweep harder and free ≤0.8 GB of pool; higher would retain ~2 GB more of a randomly-drawn remnant, worth ~27 s of avoided substitution against ~11–25 s of extra restore and +1.0 GB of pool — a wash on time, a real cost in pool. It is also what keeps the x86_64 blob bounded as the fleet grows: only the rooted floor can survive above the ceiling, and that floor is two packages, so a fleet-driven closure blow-out shows up as a slower run rather than as a pool the GC cannot shrink. **Revisit lever, not built today:** if the pool crosses the trigger below, the split is a per-leg `gc-ceiling` field in the workflow matrix feeding the single generic `gc-max-store-size`; it is worth ~0.8 GB and is not worth a mechanism until then ([ADR-032](./decisions/ADR-032-proportionate-enforcement-and-rationale.md) Rule 1).

**The pool budget.** GitHub caps each repo's cache pool at 10 GB and evicts whole entries by last-access date, oldest first; an oversized save is accepted and evicts others rather than being rejected. The knob is denominated in NAR bytes and the pool in compressed bytes, and the ratio is arch-dependent and not stable — measured 2026-08-02: x86_64-linux **1.97:1** (its store carries pre-compressed `*-firmware-*-zstd` bulk that zstd cannot re-compress), aarch64-darwin 3.49:1. Budget x86_64 at 2:1 and never at another leg's ratio — and read 2:1 as a conservative bound rather than a constant: the rooted 3.69 GB is a binary and its dependency graph, not the firmware bulk, and the rest of the saved store is drawn from the same population the 1.97:1 was measured on. The composition is new; the ratio under it is unmeasured. Occupancy re-read 2026-08-03 after the ARM64-entry deletion (#634): **4.53 GB of 10** across 3 entries. The 2026-08-02 first read showed all entries scoped to `refs/heads/main` — no `refs/pull/*` entries, so #702's second revisit trigger has not fired. Adding `nvidia-settings` (#721): its runtime closure is 1.1 GiB and its deriver-inclusive floor ≈4.24 GB (lower bound — absent requisites skipped; measured on metis 2026-08-03), which at the 2:1 budget projects ≈2.1 GB of added compressed pool, taking projected occupancy to ≈6.65 GB. Both the runtime closure and the floor exceeded the pre-stated in-band ranges (0.1–0.4 GB runtime / <1 GB added), so the entry costs more pool than the noctalia analogue predicted. The ≈6.65 GB projection did not materialize: measured steady state after the first two post-change `push: main` runs (30775710007, 30776579244) is **pool 4.40 GB / 3 entries, the x86 entry 1.94 GB — flat vs 2.07 GB pre-entry** (2026-08-03). The floor over-modelled CI retention because at steady state the store carries the rooted *runtime* closure only — the deriver-inclusive build-input graph is swept after the seeding run and never re-fetched — so the entry's steady-state pool cost is ~nil. **Revisit trigger:** pool occupancy crossing 9 GB, or any leg reporting a cold restore on a run whose `flake.lock` did not change — either means the pool is thrashing, and the answer is a binary cache for the source-built dependencies (#418), not a bigger ceiling.

**`purge-primary-key: always`** is the non-obvious one. `cache-nix-action` wraps `actions/cache`'s "primary-key hit → save is a no-op" semantic. Without `always`, a run that hits the existing primary key skips the save, so the original cache contents are cemented in the pool *even after the closure grows or the ceiling is raised*. With `always`, the action purges the primary key before the save-step's existence check, the lookup misses, GC runs against the current closure under the cap, and a fresh full cache is saved. This is the knob that needs `actions: write` (see §Permissions). Root-cause history: ADR-025 §History (#225).

**The refresh happens on push-to-main runs only; PR runs are restore-only.** This is the piece of cache mechanics that is easiest to get wrong, so it is stated here once and pointed at from every other site. `cache-nix-action` sends the purge DELETE with its `ref` pinned to `GITHUB_REF`, and GitHub's delete endpoint matches key **and** ref exactly — it has none of the base-branch fallback the *restore* path has. On a `pull_request` run `GITHUB_REF` is `refs/pull/N/merge`, a scope that holds no `nix-…` entry, because those entries are written by `push: main` runs under `refs/heads/main`. So on a PR leg the delete 404s, the action info-logs `Failed to delete the cache.` (non-fatal — it never reddens a leg), the save step then hits the surviving primary key, and the save is skipped — except in a narrow race where a concurrent `push: main` has momentarily deleted `main`'s entry, in which case the PR leg saves into its own merge-ref scope, unreadable from the default branch and harmless to `main`'s own copy (ADR-025 §History). No purge setting changes this: the prefix sweep (`purge`, `purge-prefixes`, `purge-created`, `purge-last-accessed`) is ref-scoped the same way and is likewise inert on PR runs. The result is GitHub's own recommended shape for caches under low-trust triggers — a trusted workflow on the default branch keeps the cache fresh and low-trust runs restore from it — so the enforced behaviour is the idiomatic one, not a defect. Evidence, and the dated investigation that pinned the root cause: #702 and ADR-025 §History (2026-08-02).

**Revisit trigger — restore-only on the PR legs.** The structural cure would be `cache-nix-action/restore` on PR legs (no `purge*` inputs, no post step), which makes the declaration equal the enforcement instead of relying on this paragraph. It is deliberately not done today: it costs two mutually-exclusive cache steps and a new `if:` pair whose mis-authoring breaks the cache silently in either direction, weighed against a harm that is one info-level log line ([ADR-032](./decisions/ADR-032-proportionate-enforcement-and-rationale.md) Rule 1). Adopt it if either named trigger fires: the 404 line ever masks a real failure, or PR-scoped entries start appearing in the repo's cache pool.

The cache step is also **skipped entirely** on the docs-only path (§"Docs-only short-circuit") — a cost saving rather than the correctness requirement it was originally taken for. The eviction it was meant to prevent cannot occur on a PR run: the purge 404s, the primary key survives, the save is skipped, and `main`'s entry is untouched. What the guard buys is ordinary but real — a leg that cannot save anything useful skips a full-store restore (up to ~2.5 GB as measured on 2026-08-02, 2.27 GB of it on x86_64; that span predates the rooting change, whose post-change x86_64 projection is 2.25–2.69 GB — see §"Cache sweep") and a full GC pass — and that is why it stays.

## Retry

The `nix flake check` step wraps itself in a bounded retry (3 attempts, 30s backoff). Some eval-time fetches reach third-party forges — e.g. niri's pipewire-rs from gitlab.freedesktop.org via `builtins.fetchGit` — which are **not** covered by Nix's own `download-attempts` (that retries the HTTP downloader / binary-cache fetches, left at its default of 5). A transient blip on such a forge would otherwise red `main` for a non-issue.

The retry is **blind, not regex-gated**: an earlier version matched a 19-branch stderr signature to classify transient-vs-real, brittle both ways (it can mask a real failure whose log happens to match, and miss a transient signature it didn't enumerate). Per [ADR-032](./decisions/ADR-032-proportionate-enforcement-and-rationale.md) Rule 1 (proportionate enforcement) the lighter mechanism wins, and the cost is small: the Nix store persists across attempts within a job, so a retry re-runs only the failed derivation and its un-built dependents (an eval error re-evals in seconds), not the whole closure — and a real, deterministic error still goes red, just after the retries are spent. The step's `if`-wrapped `run_checks` — the function that selects between the full `nix flake check` and the docs-only command (§"Docs-only short-circuit") — is exempt from the default `-e` errexit because GitHub's `run:` shell is `bash --noprofile --norc -eo pipefail`, and bash suppresses errexit for the whole body of a function invoked in an `if` condition.

## Timeouts

Every job sets `timeout-minutes` — a wall-time backstop on a hung leg, not a budget. GitHub's default is 360 minutes per job; with `ci.yaml`'s deliberate 3× blind retry (§Retry) a wedged `nix flake check` could otherwise burn ~18 runner-hours before GitHub killed it. The caps are sized generously over observed worst-case so a slow-but-healthy run never trips them:

- `flake-check`: **60 min**. Warm-cache runtime is dominated by the x86_64 leg, whose median was 31.8 min over ten PR runs measured 2026-08-02 (#412) — most of that a single source build the save-time sweep kept discarding, see §"Cache sweep" — while the two smaller legs finish their checks in minutes. A cold cache (a lockfile bump invalidates the key) can force a ~30–40 min Darwin closure rebuild — ADR-025 §History records a 38m53s cold first run — and the 3× blind retry can stack attempts on top. 60 min clears that with headroom.
- `gitleaks`: **10 min** (incremental scans finish in seconds).
- `flake-lock` bump: **15 min** (`nix flake update` + PR open is quick).

A job that hits its cap fails the run, which — for `flake-check` and `gitleaks`, both required — blocks the merge, the same as any other red check.

## Sibling workflows

`.github/workflows/flake-lock.yaml` (weekly lockfile bump → PR) and `.github/workflows/gitleaks.yaml` (incremental secrets scan) are decided in ADR-025 §Decision / §Rationale (cadence, manual-merge, the fine-grained PAT). `gitleaks` is now also a **required** check (see §"Display name and branch protection") and scopes its `push:` trigger to `main` so a PR branch isn't scanned twice (push + pull_request); its wall-time cap is in §Timeouts. Beyond those knobs they stay stable enough not to need a per-knob companion section here — if they grow further operational subtleties, they get their own sections rather than inline essays.
