# ADR-048: Theming delegated to Noctalia's native engine (Linux)

> Theming authority on the Linux desktop moves from Nix to **Noctalia's own native v5 engine**. The operator picks any theme — builtin, community, or wallpaper-derived — in Noctalia's own UI (control centre, launcher), and the desktop follows, including already-open foot windows via one Nix-shipped `colors_changed` repaint hook. `config.toml` declares **no theme keys** — no `source`, no `custom_palette`, no `mode` — so Noctalia's own `settings.toml` overrides layer is the sole writer, and declared-vs-runtime disagreement is impossible by construction. Nix still declares mechanism, never taste: a whitelisted builtin-template set (`foot`, `gtk3`, `gtk4`, `niri`), the pre-declared mount-points those templates write into, and the repaint hook. This **reverses [ADR-044](./ADR-044-linux-runtime-theme-menu.md) for Linux** (Nix is no longer the theming authority there; the conductor — `home/nixos/theme-menu.nix`, the `theme` CLI, the `hooks.started` polarity reconcile, `portal-color-scheme.nix` — is **deleted**, not deprecated in place) and **amends [ADR-041](./ADR-041-terminal-authority-tui-theming.md)'s Linux scope** (template-first per-tool theming, with the terminal-ANSI bus surviving as the fallback authority for untemplated TUIs). Colour joins **[ADR-036](./ADR-036-noctalia-shell-linux-desktop.md)'s declared-core/mutable-skin posture** on the mutable-skin side. **Darwin (celaeno) is untouched** — it keeps the ADR-044 conductor and its ADR-041 arrangement; `lib/scheme-pair.nix`'s whole-catalogue `.menu` resolver becomes a Darwin-only consumer in practice.

## Context

ADR-044 made Nix the single theming authority on the Linux desktop: a declared family catalogue, rendered per-entry at build time, switched atomically by the `theme` CLI. It works and is the most runtime-probed subsystem in this repo. But #770's operator dialogue (2026-08-13) named the frictions directly: the switch's only surface is a terminal CLI while Noctalia's shell owns the launcher and control centre; Noctalia's own theme pickers are inert-by-convention, guarded only by discipline against a sidecar that can shadow declared config with no mechanical protection, and the lived experience of that half-dead surface was "clunky, annoying and counter-intuitive" (operator evidence, 2026-08-13); and the declared catalogue forecloses the ecosystem Noctalia v5 ships natively — community palettes, wallpaper-derived schemes, templated true-colour theming beyond the ANSI-16 approximation ADR-041 accepted for TUIs.

The dialogue settled the user-facing model on the operator's terms: theming ties to Noctalia specifically, its switching UI is the primary gesture, community and wallpaper-driven themes are core UX not options, and macOS/NixOS are treated separately with accepted drift. The full forces, options considered, and de-risk evidence (a dedicated 2026-08-13 research-and-adversarial-verification workflow plus the G2/G3 spike program) are recorded in [`docs/design/noctalia-theming-delegation.md`](../design/noctalia-theming-delegation.md), the design note this ADR freezes — not restated here (ADR-032 single-sourcing).

## Decision

**1. Noctalia is the single theming authority on the Linux desktop.** Theme state lives solely in `~/.local/state/noctalia/settings.toml`, written by Noctalia's own GUI/IPC — the intended channel, not drift. `config.toml`'s `[theme]` table (`home/nixos/noctalia.nix`) declares **no keys**: no `source`, no `custom_palette`, no `mode`. A fresh host renders Noctalia's own defaults; the first runtime pick just works and persists — colour-conductor force 2 ("a fresh reprovision lands on the declared look") is consciously retired, not silently dropped.

**2. A whitelisted builtin-template set is enabled, exactly four ids.** `theme.templates.enable_builtin_templates = true` with `builtin_ids = [ "foot" "gtk3" "gtk4" "niri" ]` — whitelist-form, never blanket (CLAUDE.md stance). `starship` and `btop` are excluded: the G3 spike's starship incident found both tools' builtin `apply.sh` run `sed -i` against the discovered config path with no read-only awareness, materializing a plain file over an HM-owned symlink — a real, disclosed safety incident against the operator's live `STARSHIP_CONFIG`, remediated same-session (design note §De-risk). starship's constructive route is a future user-template with an explicit `output_path`, not this builtin. `helix` and the remaining community ids are deferred post-cutover pending their own G3-shaped acceptance testing. Qt has no target on this desktop (#103, ADR-028) and stays out. `theme.templates.enable_community_templates = false` — a separate, unreviewed trust surface (arbitrary `apply.sh` via `/bin/sh -lc`, no sandboxing) staged for after cutover; community **palettes** need no enablement at all and are part of the UX regardless, picked directly in Noctalia's own UI.

**3. Mount-points are pre-declared, not runtime-hooked.** `home/nixos/foot.nix` declares `include = "~/.config/foot/themes/noctalia"` (foot's builtin `apply.sh` detects it via a loose `grep 'include.*noctalia'` against `foot.ini`); `home/nixos/niri.nix` appends `include optional=true "noctalia.kdl"` to the rendered config (niri's builtin `apply.sh` detects it via a basename-anchored regex, resolved relative to niri's own config directory). Both patterns are G3 on-metal-confirmed in both directions: include present → the template writes only its own theme file, never the HM-owned config; include absent + read-only → a clean, non-destructive abort (foot: symlink materialization surfaced only at the next `nh os switch`, not live; niri: atomic `EACCES`, no materialization). GTK takes a different, deliberately-decided path: its `apply.sh` has no pre-declared-include pattern — it detects the HM-owned read-only `gtk.css` symlink and materializes it into a plain file with its own `@import` appended, idempotently on every re-run. This is a per-tool **ownership release**, decided on G3 evidence, not an oversight — `home/nixos/stylix-targets-desktop.nix` drops its own conductor-owned `gtk.extraCss` override in favour of it.

**4. The terminal repaint hook.** `home/nixos/noctalia.nix` binds `hooks.colors_changed` (fires strictly after every template finishes writing, source-guaranteed by the single template worker) to a Nix-shipped, `writeShellApplication`-built script. It receives no environment — the hook command runs via `/bin/sh -lc` with no variables passed — so it reads Noctalia's own rendered foot theme file itself and re-points the #609-proven per-pty OSC loop (OSC 4×16 + 10/11, `pgrep`→`ps` discovery — an explicit pty walk, never a signal-by-name) at it, then nudges niri explicitly (`niri msg action load-config-file`, since niri's inotify watch misses the write — niri#2658, the same gap the retired conductor's CLI worked around). The hook fires 3-4× per change at the pinned tag (`v5.0.0-beta.8`) plus once on an unrelated reload — the upstream dedup commit (`460d1d4fc`) does not deliver 1:1 in practice — so **idempotency and cheapness are permanent requirements**, not transitional ones, and the hook reports failure honestly to a state-dir log file rather than swallowing a missing theme file or a dead pty (#303 — no unconditional success).

**5. The ADR-044 conductor is deleted on Linux, not deprecated in place.** `home/nixos/theme-menu.nix` (entry-dir renders, the `theme` CLI, the seed activation), the `[hooks] started` polarity reconcile, and `home/nixos/portal-color-scheme.nix` (its sole reason for existing — the gated dconf write — is gone; Noctalia's own gtk template's `apply.sh` is now the sole polarity writer, via gsettings with a dconf fallback) are all removed from the Linux tree and its bundle. `lib/theme-families.nix`'s `defaults.<host>` entries for alcyone/alnair/electra are **retained** but their meaning narrows: they feed only `modules/nixos/stylix-palette.nix`'s single-scheme boot default (`.select .polarity`) — the Stylix base16 palette a fresh build/reprovision renders before any runtime pick — never the whole-catalogue `.menu` resolver (`lib/scheme-pair.nix`), which becomes a Darwin-only consumer in practice; no Linux file imports it post-cutover. celaeno's entry is unaffected on both axes.

**6. Darwin is untouched, explicitly.** `home/darwin/theme-menu.nix`, the Darwin conductor's CLI, and celaeno's ADR-041 arrangement are unaffected by any item above. `lib/theme-families.nix`, `lib/scheme-pair.nix`, and `lib/palette-for.nix` remain shared files, but item 5's narrowing is Linux-specific: celaeno still consumes the full catalogue.

## Rationale

**Template-first, bus-fallback (operator policy, 2026-08-13).** Where a template exists for a surface and clears the three G3 acceptance gates — no mutation of HM-owned files (a pre-declared mount-point, or a deliberate ownership release decided on evidence), a reload path that meets the instant bar, and a rendered result that meets the operator's standards on-metal — the template themes the surface in the theme's true colours, not the ANSI-16 projection. This amends ADR-041's Linux scope: the terminal-ANSI bus remains the fallback authority for any tool without a passing template (today: every TUI except the four whitelisted above), not the default for every TUI on Linux. Darwin's ADR-041 arrangement is untouched — its per-tool ANSI-mode configs stay exactly as ADR-041 left them.

**Reproducibility force retired, not silently dropped.** ADR-044's mechanism gave "a fresh reprovision lands on the declared look" for free; that force is now explicitly retired for Linux (design note §Drawbacks, "Authority surrendered") — recourse for an off-looking pick is picking another theme, not patching slots in git. This is the same trade ADR-036 already signed for shell layout/cosmetics (declared-core/mutable-skin); colour simply joins it.

**One writer, structurally — the seam ADR-044's own "explicit triggers, no passive watch" rule anticipated.** ADR-044 already established that no surface gets a passive-watch assumption without runtime verification; this decision applies the same discipline one level up — no *declared* theme key gets left in place without a verified writer story, because leaving even one (`source`, `mode`, a boot default) would keep the exact two-writer seam ADR-044's own §Rationale worked to close, just inverted (Nix racing Noctalia's sidecar instead of Noctalia racing a symlink).

**A network edge opens, consciously.** Community palettes *and* templates fetch from `api.noctalia.dev` into live state — a community template is remotely-fetched *write behaviour* (output paths, hooks, `apply.sh` via `/bin/sh`), not just colour data. Accepted as a deliberate, bounded exception to the whitelist stance: community templates stay off at cutover (item 2), and any future enablement is per-id, G3-tested first (relates #579/#568).

## Consequences

- ✓ The pre-built UX the operator wants: theme switching happens in Noctalia's own surfaces, no CLI required, and the full ecosystem (builtin, community, wallpaper-derived) is reachable with zero repo edits.
- ✓ No inert pickers, no must-not-touch convention, no reconcile machinery — Noctalia's control centre pickers are the intended, primary gesture now, not a trap.
- ✓ TUIs with a passing template render in true colour instead of the ANSI-16 approximation; every other TUI keeps ADR-041's polarity-correct-everywhere guarantee unchanged.
- ✓ One writer, structurally: no declared theme key exists to disagree with the sidecar.
- ✗ Lifecycle re-coupling: theming re-binds to Noctalia's lifecycle — the exact coupling ADR-044 was built to escape after DMS died (ADR-029) and v4→v5 forced a rewrite (#644). A third, conscious bet on v5's momentum.
- ✗ Reproducibility is gone for colour: a fresh reprovision no longer restores the operator's look; no mechanism guarantees runtime state matches anything declared (accepted, "declared core, mutable skin" extended to colour).
- ✗ An activation-window hazard, mechanically closed for foot: between `nh os switch` and Noctalia's next theme resolve the template outputs do not yet exist; foot's fatal missing-include (exit 230) is closed by a seed-if-absent activation placeholder (`noctaliaFootThemeSeed`, operator ruling at #824 — never touches a live theme file), and the remaining GTK window is cosmetic only (Stylix's static base16 until the first resolve). See `docs/desktop/noctalia.md` §Sharp edges.
- ✗ Beta authority: the engine is beta with active config-migration churn and thin tests; the per-bump ritual (hook surface, template inventory, sidecar semantics, polarity writer) grows accordingly — unchanged in kind from ADR-044's own beta-authority cost, but now covering a wider surface (templates, not just the engine).
- ⚠ Migration trigger: if Noctalia's native `color-scheme` write (`b664d3c`, absent from every released tag as of beta.8) ships in a future release, the gtk template's `apply.sh` polarity write becomes redundant rather than wrong — no action required, but worth confirming at the next bump.
- ⚠ Migration trigger: if a future community template clears its own G3-shaped acceptance gates, `enable_community_templates` and its `community_ids` whitelist get the same explicit, per-id treatment item 2 gave the builtins — never a blanket flip.

## Amendment to ADR-044

**Reversed for Linux, unaffected for Darwin.** Every decision item in ADR-044 — the per-entry derivation catalogue, the two-axis persistence model, the `theme` CLI, the seed activation, the Noctalia-demotion recipe — described the Linux desktop specifically and is superseded there by this ADR's Decision above. ADR-044 continues to describe Darwin's `home/darwin/theme-menu.nix` conductor unchanged; nothing in that implementation is touched by this decision.

## Amendment to ADR-041

**Linux scope only: template-first, bus-fallback**, per this ADR's §Rationale. The terminal-ANSI bus (bat `base16`, helix `base16_terminal`, fzf `--color=16`, zellij `ansi`, starship/lazygit native ANSI names, yazi dual presets) remains the *fallback* authority for any Linux TUI without a passing, whitelisted template — today, every TUI except foot, gtk3/gtk4, and niri, none of which ADR-041 covered as TUIs in the first place (foot is the terminal itself; gtk/niri are chrome, not TUIs). ADR-041's actual TUI surface (bat/helix/fzf/zellij/starship/lazygit/yazi) is therefore **unaffected in practice today** — this amendment records the scope rule for future template adoptions (helix and the deferred community ids), not a present behavioural change. Darwin's ADR-041 arrangement is entirely untouched.
